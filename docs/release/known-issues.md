# Known Issues — RC v1.0.0 (TASK-115)

> Реестр известных проблем, с которыми RC выходит к кандидату v1.0, и их триаж
> по правилам §13 TASK-115 (блокер / major / пост-MVP). Заполняется из двух
> источников: (а) известные до-RC находки автотестов и аудитов — ниже; (б) находки
> ручного прогона по `rc-checklist.md` — раздел 2. Критерий §20: major-дефект
> либо исправлен, либо подписан здесь владельцем.

## 1. Известные до-RC находки (триаж выполнен, подпись владельца — при go/no-go)

### KI-1 · Изоляция Chromium-слоя не полна (F2 аудита 106)

- **Симптом:** `HL_TEST_USER_DATA` изолирует контейнер (БД/vault), но не
  Chromium-слой: localStorage (в т.ч. `hl.updates.lastCheckAt`) и кэши живут в
  реальном профиле и шарятся между e2e/аудит-прогонами и пользовательскими
  данными (`docs/architecture/audits/2026-Q1-mvp.md` §4).
- **Триаж (§13):** **пост-MVP**. Не потеря/порча данных, не краш основного
  потока, не обход сетевых границ (несанкционированной активности нет — вердикт
  аудита PASS после фикса F1): затронута изоляция тестовой/аудитной среды, а не
  продуктовые обещания. Влияние на RC-прогон: сверка «журнал сети ↔ UI-состояние»
  на «чистой» машине неполна (негативный localStorage) — компенсируется
  скриншотами ленты, как в S2/S3 аудита 106.
- **План:** задача TASK-119 (фикс-кандидат: `app.setPath('userData', override)`
  в bootstrap при заданной переменной).

### KI-2 · Локальные no-tag сборки без `resources/app-update.yml` (F3 аудита 106)

- **Симптом:** electron-builder генерирует `app-update.yml` только в
  publish-manager-пути (на теге в CI); локальные сборки без тега его не получают
  — следствие: «Проверено: …» из localStorage (KI-1) воспроизводилось в свежих
  профилях локальных аудитов.
- **Триаж (§13):** **пост-MVP / наблюдение**. CI-сборки не затронуты
  (`stable.yml` в draft прогона v0.9.0-rc.0 это подтвердил); на установку и
  обновление из официального фида не влияет. Самостоятельного дефекта нет
  (следствие KI-1).
- **План:** задача TASK-120 (наблюдение; детерминированный publish-блок для
  локальных сборок).

### KI-3 · Тёмная тема на светлой ОС: вторичный текст ниже контраста (10.1 аудита 109) — ЗАКРЫТА TASK-123 (05.10: все цветовые решения через токены, классы dark: удалены из рендерера)

- **Симптом:** не-токенные палитры Tailwind с `dark:` (prefers-color-scheme ОС)
  не следуют `data-theme` приложения; при явной тёмной теме на светлой ОС
  вторичный текст ≈2.2:1 (`docs/a11y-nvda.md` §10.1, probe-факт).
- **Триаж (§13):** **major, документируется** (критерий блокера — краш/данные/
  безопасность/установка — не задет; §16 RC повторяет только ключевые
  NVDA/axe-пункты). Согласуется с реестром отложенных: исправление — миграция на
  токены, триггер «первая задача P7-полировки».
- **План:** задача токен-миграции (триггер из `docs/a11y-nvda.md` §10.1);
  до неё пользователю доступен обход — явная светлая тема ОС или темы
  приложения.

### KI-4 · Границы полей ввода ниже 3:1 (10.2 аудита 109) — ЗАКРЫТА TASK-123 (токен input-border ≥3:1 на surface, пара в контраст-аудите)

- **Симптом:** `--hl-border` 1.42:1 (light) / 1.72:1 (dark) — ниже не-текстового
  минимума WCAG 1.4.11 для опознания полей ввода (`docs/a11y-nvda.md` §10.2).
- **Триаж (§13):** **major, документируется** (та же логика, что KI-3; поля имеют
  видимые подписи — placeholder не носитель информации, §17 ревизии 110).
- **План:** тот же заход токен-миграции (KI-3); строки сверяются с
  `docs/a11y-deferred.md`.

### KI-5 · Остаточные риски сетевого аудита (методика, не дефекты)

- Sub-500-мс соединения между тиками polling 500 мс недаблюдаемы — вторая линия
  защиты: depcruise-запрет прямых net/fetch вне EgressGateway
  (`2026-Q1-mvp.md` §5).
- S4-цикл отзыва сокращён; инвариант «попытка без согласия → 0 сети» покрыт
  прогонами S1/S3.
- Оговорка updater-байтов (TASK-096 §22) — применить при первом успешном
  обновлении по фиду на машине B (`rc-checklist.md` §3).
