# Health Log — дорожная карта реализации

**Статус:** v0.1 · 2026-09-24 · ветка `docs/planning` · базируется на SRS v0.1 (`docs/01–10`) и архитектуре v0.1 (`docs/architecture/01–10`)

Принципы карты:

1. **Каждая фаза заканчивается работающим продуктом** — можно установить, запустить и пользоваться тем, что уже сделано.
2. **Долг минимизируется порядком, а не обещаниями:** всё, что дорого менять потом (контракты, схема БД, шифрование, i18n, правила границ), строится в фазах 0–1; всё, что дёшево добавить (фичи поверх ядра) — позже.
3. **Один разработчик, вертикальные срезы:** фаза = набор эпиков; эпик = веха с демонстрируемым результатом; задачи 0,5–4 часа.
4. Оценки: **S** = 0,5–1 ч, **M** = 1–2,5 ч, **L** = 2,5–4 ч чистой работы. Итого ≈ 90 задач, ~180–200 ч (без учёта приобретения сертификата подписи и подбора моделей).

## Вехи (иерархия эпик → веха → задачи)

## Рекомендуемый порядок разработки (один человек)

Строгое ядро: P0 → P1.1 → P1.2 → P1.3 → P1.4 → P2 → P3 → P4 → P5 → P6 → P7.

Ключевые отклонения от «чисто последовательного»:

1. **Шифрование сразу (P1.2), а не «потом»:** перевод незашифрованной БД на SQLCipher — это миграция данных и риск; дороже на 20% сейчас, дешевле в 10 раз потом.
2. **i18n-каркас в P0:** ретрофит ключей в готовые экраны — классический долг; тексты с первого дня — только ключи.
3. **Упаковка в конце P1 (P1.4):** «работает только в dev» — самый дорогой вид долга; билд-проблемы вскрываются рано.
4. **PDF и копии (P4) до ИИ (P5):** отчёт врачу и копии — ядро ценности без зависимости от моделей; ИИ — самая рисковая часть (R-3) и стоит последней в функционале.
5. **Если время поджимает:** минимальный MVP = P0–P4 + 5.1–5.5 (без чата и ночных eval) + 6.3 + 7.1; красный набор и полная доступность — до публичного релиза обязательно (гейты DoD SRS 10).

## Технический долг, отложенный намеренно

Каждая позиция: что откладываем · почему допустимо · триггер пересмотра.

| # | Долг | Почему допустимо сейчас | Триггер пересмотра |
|---|---|---|---|
| TD-1 | Синхронный SQLite в main-процессе (без асинхронного слоя) | Объёмы ≤50k строк, индексы; тяжёлое — в воркерах (арх. 03 §6) | Запросы >100 мс в профилировке |
| TD-2 | Даун-миграций нет, откат = восстановление автокопии | Проще и безопаснее для соло-разработки | Появление внешних потребителей схемы (синхронизация) |
| TD-3 | Профили: один seeded-профиль, UI мультипрофиля нет | Схема готова (`profile_id`), изоляция в репозиториях | Эпик FR-11 (пост-MVP) |
| TD-4 | Каталоги локализации: только `ru`, инфраструктура i18n готова | Аудитория RU (A-5); ключи с первого дня — ретрофита не будет | Эпик EN (пост-MVP) |
| TD-5 | Оптимистичных обновлений UI нет | Локальная запись ~мс; риск рассинхрона нулевой | Если появится сетевой слой |
| TD-6 | E2E в CI — только с P7 (локально — с P1) | Windows-runner + Playwright Electron дорог в раннем CI | Первый публичный beta |

| TD-8 | Статистика без инкрементальных кэшей (пересчёт по запросу) | Быстро на целевых объёмах (NFR-4); кэш = состояние = баги | Профилировка показывает >1 с на период |
| TD-9 | Флаги — только локальные, без удалённого управления | Сеть против FR-7.3; каналы релизов выполняют ту же роль | Командное распределённое развитие |
| TD-10 | Печать напрямую с принтера отсутствует (PDF → просмотрщик) | 95% сценария закрыто (FR-6.7) | Явный спрос пользователей |

## Правила ведения карты

- Задача считается выполненной только с её разделом «Проверка» (тесты/ручной прогон), а не «код написан».
- Новая работа вне карты = сначала ревизия карты (защита от R-5 SRS).
- Оценки пересматриваются в конце каждой фазы; накопленное отклонение >25% — повод пересобрать оставшиеся фазы.
