# ADR-0005: Подпись Windows-сборок — OV-сертификат как MVP-дефолт

**Задача:** TASK-104 · **Дата:** 2026-10-02 · **Статус:** принято (условие пересмотра — §6)
**Связанные решения:** NFR-11 (updater проверяет подпись установщика), D15 (арх. 10 §2 — release-инженерия), TASK-096 (electron-updater), TASK-105 (релизный пайплайн); рабочий процесс — `docs/dev/certificates.md`

---

## 1. Контекст

Неподписанный установщик Windows даёт двойной эффект: SmartScreen/антивирусы
предупреждают («неизвестный издатель») — конверсия установки падает; electron-updater
проверяет подпись скачанного обновления (NFR-11) — без publisherName/подписи
механика автообновления неполноценна и небезопасна. Сертификат — внешний процесс
закупки (стартует со спринта 6), поэтому механика подписи и фида проверялась
самоподписанным сертификатом (test-cert), а боевой тип сертификата нужно было
зафиксировать заранее.

Выбор: OV (Organization/Individual Validation, файл `.pfx`, недорого) или
EV (Extended Validation, аппаратный токен/HSM, мгновенная SmartScreen-репутация,
дорого).

## 2. Решение (выбранный путь)

**OV Code Signing, файл `.pfx`, подпись через electron-builder signtool-стек
(sha256 + RFC3161-timestamp) — MVP-дефолт.**

Аргументы:

- **Достаточно для механики:** OV-подпись удовлетворяет проверку updater'а
  (publisherName = Subject DN в `app-update.yml`) и снимает «неизвестный издатель»;
  SmartScreen-репутация набирается от числа установок (первые недели — возможны
  предупреждения: коммуникация в release notes, TASK-114).
- **Простой пайплайн:** `.pfx` кладётся в GitHub Encrypted Secrets
  (`WIN_CSC_LINK` base64 + `WIN_CSC_KEY_PASSWORD`) — без токена/сервиса; локальная
  контрольная подпись — env-файл вне git (соглашение `*.local`).
- **Цена/срок:** 20–120 €/год против ~300–700 $/год + физический токен у EV;
  выпуск — дни, без организационных проверок (для individual — Certum OSS/SSL.com).
- **RFC3161-timestamp обязателен** (`signtoolOptions.rfc3161TimeStampServer`):
  подпись переживает истечение сертификата — обновления у пользователей остаются
  валидными (контроль — наличие tsa-URL в signtool-вызове лога, §13 TASK-104).

## 3. Альтернативы

- **EV (токен/HSM):** мгновенная SmartScreen-репутация. Отклонено для MVP: заметно
  дороже, токен несовместим с «секрет в CI» — потребуется подпись-сервис (HSM) или
  запуск подписи на отдельном runner с токеном, что меняет пайплайн (TASK-105) и
  добавляет операционный риск. **Условие пересмотра:** устойчивый поток жалоб на
  SmartScreen-предупреждения после релиза (данные — счётчики установок/жалобы из
  release notes, смотришь в 114) — тогда EV или Azure Trusted Signing пересматриваются.
- **Azure Trusted Signing:** подпись как сервис, дешёвый, без токена; но требует
  Azure-аккаунта/identity validation и иного секрета-провайдера; оставлен как
  альтернатива при пересмотре (electron-builder 26 поддерживает `azureSignOptions`).
- **Остаться без подписи:** блокирует NFR-11 и конверсию установки — отклонено.

## 4. Секреты-процесс

- `.pfx` + пароль — GitHub Encrypted Secrets (`WIN_CSC_LINK`, `WIN_CSC_KEY_PASSWORD`),
  доступ — только релизный workflow (TASK-105); PR-пайплайн секрет не получает
  (OWASP CI/CD: код PR не исполняется в привилегированном контексте).
- Локально — env-файл вне git (`apps/desktop/cert.env.local`, соглашение `*.local`
  в корневом `.gitignore`; `*.pfx`/`*.pem` игнорируются явно).
- В конфиге `electron-builder.yml` секретов нет — сторожит конфиг-тест
  (`update-feed.test.ts`: «секреты подписи не в конфиге»); там же — только
  не-секретные параметры: `signingHashAlgorithms: [sha256]`,
  `rfc3161TimeStampServer`, `publisherName`.
- Пароль в логи не попадает: electron-builder печатает факт подписи и имя
  сертификата, не пароль.
- publisherName (2 места конфига — `publish.publisherName` и
  `win.signtoolOptions.publisherName`) должен равняться Subject DN сертификата —
  это контракт updater'а (проверка подписи скачанного обновления, NFR-11); паритет
  мест проверяется конфиг-тестом.

## 5. Продление

- Срок OV — 1–3 года. RFC3161-timestamp сохраняет валидность уже выпущенных
  подписей после истечения, но новые сборки требуют действующий сертификат.
- Календарное напоминание за 60 дней до NotAfter — в release-процессе (TASK-114).
- Продление/замена: новый `.pfx` → подмена секрета (certificates.md §2), обновление
  publisherName по DN (если изменился), контрольная подпись (§3), сводка в этом ADR
  (§7).

## 6. Условие пересмотра решения

Жалобы на SmartScreen после релиза MVP (метрики TASK-114): если доля установок с
прерыванием на предупреждении устойчиво значима — пересмотр в пользу EV или
Azure Trusted Signing (оценка цены пайплайна с токеном/сервисом отдельной задачей).
