# ADR-0002: SQLCipher-стек better-sqlite3 (шифрование в покое)

**Задача:** TASK-022 · **Дата:** 2026-09-26 · **Статус:** принято
**Связанные решения:** D4 (арх. 04 §1 — SQLite + WAL + SQLCipher), NFR-2 (шифрование по умолчанию), NFR-4/9 (порог производительности — TASK-111)

---

## 1. Контекст

NFR-2 требует шифрование БД в покое включённым по умолчанию, без действий пользователя.
Решение «шифровать сразу» (фаза P1, дорожная карта) зафиксировано до появления данных:
перевод незашифрованной БД на шифрование позже — миграция данных и риск потери доверия.
Нужен рабочий better-sqlite3 с SQLCipher под Electron ABI, автоматизированная повторяемая
пересборка и понятные ошибки (STORAGE/*) вместо крипто-мусора.

## 2. Решение (выбранный путь)

**Community-пресет `better-sqlite3-multiple-ciphers` (m4heshd) v13.0.3** — fork better-sqlite3
с поддержкой SQLite3MultipleCiphers; SQLCipher-совместимый режим включается прагмой
`cipher='sqlcipher'` (задаётся строго ДО `PRAGMA key`), дефолты шифра — дефолты SQLCipher 4.

Аргументы выбора:

- **Node-API (v13):** один prebuilt-бинарник на платформу (`prebuilds/win32-x64.node`),
  ABI-независимый между node и Electron; требование версий — node ≥ 22, Electron ≥ 35
  (у нас: node 24.13.0, Electron 44.4.5). Проблема «пресет отстаёт от ABI Electron» (§22
  как главный риск фазы) для v13 снята по построению — пересборка под ABI не нужна.
- **Prebuilds bundled в npm-пакет:** установка без сети и без компилятора; pnpm-конфиг
  `neverBuiltDependencies: [better-sqlite3-multiple-ciphers]` отключает спускаемый
  node-gyp rebuild (у пакета есть binding.gyp — pnpm иначе запускает сборку из исходников,
  которая падает без VS Build Tools; бинарник и так грузится из prebuilds/ в рантайме).
- **SQLCipher-совместимость:** формат БД открывается SQLCipher-инструментами
  (SQLiteStudio и т.п.); ключ — raw hex 32 байта (`PRAGMA key = "x'<hex>'"`, KDF не
  применяется — ключ и так случайный, арх. 04 §6).
- **Сопровождение:** fork активно отслеживает upstream better-sqlite3 (v13 = upstream v12
  + ciphers, SQLite 3.53.4); TypeScript-типы bundled.

Точка входа — обёртка `openEncrypted(path, keyHex)` (`apps/desktop/src/main/shared/db/sqlite.ts`),
единственная точка открытия БД в проекте (контейнер TASK-027). Порядок прагм: `cipher` →
`key` → `quick_check` (проверочное чтение первой страницы: неверный ключ даёт SQLITE_NOTADB
на открытии, а не крипто-мусор при первом запросе; заодно детект повреждения при старте —
полный сценарий восстановления TASK-100/101) → `journal_mode=WAL` → `foreign_keys=ON` →
`synchronous=NORMAL`.

Пересборка автоматизирована `apps/desktop/scripts/prepare-native.sh` (postinstall,
`pnpm run prepare-native`, обёртка `.cmd` для cmd): гейты окружения (node ≥ 22, Electron ≥ 35)
с понятным отказом — «тихой» сборки без шифрования не бывает (§22 TASK-022); smoke-тест
(открыть с ключом → вставить → закрыть → переоткрыть → прочитать; неверный ключ →
SQLITE_NOTADB; первые байты файла ≠ SQLite-магии); при провале — electron-rebuild
(потребует компилятор) и повторный smoke. Флаг `--electron-smoke` прогоняет тот же smoke
под рантаймом Electron — проверено на Electron 44.4.5 (exit 0).

## 3. Альтернативы

1. **`@journeyapps/sqlcipher`** — SQLCipher-форк better-sqlite3 с prebuilt только под node
   (NAN, per-ABI); под Electron 44 — обязательная сборка из исходников (VS Build Tools на
   каждой dev/CI-машине), база отстаёт (better-sqlite3 v7). Отвергнуто: тяжеловеснее и
   менее сопровождаемо, чем v13-пресет.
2. **Сборка better-sqlite3 + SQLCipher из исходников** (`npm_config_build_from_source`,
   связка openssl/csql) — максимальный контроль, но компилятор + стратегия обновления на
   каждой машине; оставлен как fallback-путь внутри prepare-native (electron-rebuild).
3. **План Б: обычный better-sqlite3 + шифрование файла целиком при закрытии** (AES-GCM,
   ключ из KeyVault) — менее гранулярно: БД не читается во время работы приложения без
   расшифровки всего файла, WAL/журналы вне контроля, крэш-консистентность — на приложении.
   Рабочий запасной вариант, не потребовался.
4. **Vanilla better-sqlite3 + шифрование полей** — отвергнуто ранее в D4: частичное
   шифрование ошибается на индексах/поиске; SQLCipher шифрует файл целиком (включая WAL).

## 4. Компромиссы

- **Community-fork вместо upstream:** риск сопровождения (§22 TASK-022) — mitigирован
  активностью форка и плана Б; обновление пресета — только с compat-тестом переоткрытия
  БД, созданной предыдущей версией стека (§23 TASK-022, TASK-105).
- **Node ≥ 22 / Electron ≥ 35:** floor по версиям рантаймов пресета v13. На неподдерживаемом
  окружении скрипт/приложение фейлятся понятно (prepare-native: exit 1 с причиной), а не
  собираются тихо без шифрования. Целевая платформа x64 Windows; macOS/Win-arm — post-MVP
  (пресет несёт prebuilds win32/darwin/linux x64+arm64 — запас есть).
- **`synchronous=NORMAL`** (§8 TASK-022): WAL+NORMAL переживает краш процесса; риск потери
  транзакции остаётся только при краше самого диска (power loss). FULL дал бы durability на
  дисковом сбое ценой скорости на каждом коммите — для локального дневника принято NORMAL;
  пересмотр при появлении требований к durability выше.
- **KDF выключен (raw hex-ключ):** PBKDF2 не нужен — ключ генерируется CSPRNG (32 байта) и
  хранится обёрнутым (safeStorage/пароль-обёртка, TASK-023, арх. 04 §6). Если когда-нибудь
  ключом станет человеческий пароль — потребуется обёртка Argon2id поверх (учтено TASK-023).
- **JS-гарантий обнуления ключа в памяти нет** (§14 TASK-022): hex-строка передаётся в
  PRAGMA как часть SQL-строки; GC-время жизни не контролируется. Задокументировано; защита —
  ключ никогда не логируется (redact-список PHI_KEYS/PHI_REDACT_PATHS дополнен `keyHex`/`key`)
  и не покидает main-процесс.
- **better-sqlite3 синхронный:** блокирует main на время запроса — принято в D4 (арх. 03 §6,
  TD-1: объёмы ≤ 50k строк, тяжёлое — в воркерах).
- **busy-timeout 5000 мс (дефолт better-sqlite3):** конфликт блокировок на открытии ждёт до
  5 с, затем `STORAGE/LOCKED`. Сценарий редкий (single-instance, TASK-012); переопределение
  таймаута не вводилось — не специфицировано TASK-022, пересматривается при первом живом
  сценарии (TASK-027+).

## 5. Производственная базовая линия (§15 TASK-022)

Замер: 1000 вставок единой транзакцией в зашифрованную БД (`cipher='sqlcipher'`, дефолты,
WAL, `synchronous=NORMAL`), тест `sqlite.int.test.ts` («1000 вставок в транзакции ≤ 1000 мс»):

| Окружение | Результат |
|---|---|
| dev-машина: Windows 10.0.26200 x64, node 24.13.0, пресет 13.0.3 (prebuilt win32-x64) | **1,2–1,3 мс** за 1000 вставок (два прогона) |

Порог §15 (≤ 1 с) перекрыт на три порядка; базовая линия для NFR-4/9 — порог оценивается в
TASK-111. WAL обязателен: без него вставки в 10+ раз медленнее (§15) — обёртка выставляет
`journal_mode=WAL` при каждом открытии (режим персистентен в заголовке файла, тест
переоткрытия фиксирует `wal`).

## 6. Проверка (§20/§24 TASK-022)

- интеграционный набор `sqlite.int.test.ts` — 8/8 зелёные (roundtrip с ключом; неверный/отсутствующий
  ключ → STORAGE/BAD_KEY; первые 16 байт ≠ «SQLite format 3\0»; WAL-файлы и journal_mode после
  переоткрытия; чужой блокировка → STORAGE/LOCKED; замер ≤ 1 с; keyHex-валидация);
- `pnpm run prepare-native` — exit 0 дважды, sha256 бинарника между запусками неизменен
  (идемпотентность, §24); smoke дополнительно проверен под рантаймом Electron 44.4.5
  (`--electron-smoke`, exit 0);
- коды `STORAGE/BAD_KEY`, `STORAGE/LOCKED`, `STORAGE/CORRUPT` в реестре kernel (§13);
  `STORAGE/CORRUPT` детектится `quick_check` при открытии, полный сценарий — TASK-100/101.
