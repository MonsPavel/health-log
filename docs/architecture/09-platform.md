# 09. Платформенные сервисы: jobs, уведомления, кэш, флаги, конфигурация, наблюдаемость, ошибки, офлайн

**Статус:** черновик v0.1 · 2026-09-24

---

## 1. Фоновые задачи

**JobScheduler** в main-процессе: реестр задач (имя, интервал, окно простоя), запуск по таймеру с проверкой «приложение активно/простаивает». Никаких внешних очередей — задачи локальны и идемпотентны.

| Задача | Когда | Назначение |
|---|---|---|
| `db.maintenance` | простой, еженедельно | PRAGMA optimize, integrity-check, ротация событий |
| `ai.unload` | таймер простоя воркера | выгрузка модели, освобождение RAM (07 §1) |
| `updates.check` | интервал, **только при согласии** | проверка релизов (FR-7.3, NFR-11) |
| `backup.reminder` | еженедельно, если копии нет >14 дней | мягкая подсказка UI (R-4) |
| `reminders.measure` | пост-MVP FR-10 | см. §2 |

**Почему не node-cron/очереди (BullMQ и т.п.):** внешние зависимости ради пяти таймеров; планировщик — 50 строк за портом, тестируется фейковыми часами.

## 2. Уведомления

- **Внутренние:** баннеры/панели UI — критические значения (FR-7.4), стейлс резюме, ошибки сети. Это основной канал MVP.
- **ОС-уведомления (Electron Notification):** пост-MVP напоминания об измерении (FR-10) с тихими часами и тоном без упрёков; клик уведомления → открытие формы ввода.
- Номера экстренных служб — из реестра локали (FR-7.4).

## 3. Кэширование

| Уровень | Что кэшируется | Инвалидация |
|---|---|---|
| TanStack Query (renderer) | read-models (списки, статистика, серии) | события `measurement:changed`, `data:versionBumped` |
| main, в памяти | активная шкала (`reference_scale`), префы, реестр моделей | по версии/мутации настроек |
| БД | `ai_summary` по `context_hash` | стейлс через `data_version`; удаление вручную (FR-6.5) |
| Диск | файлы моделей (immutable, sha256) | не инвалидируется, только удаление |

Расчёты (статистика) намеренно **не** кэшируются в main: они быстры на целевых объёмах (NFR-4), а кэш доменных вычислений — лишнее состояние. **Почему без Redis-подобного слоя:** один процесс, ноль сети; смысл кэша здесь — отзывчивость UI, а не разгрузка сервера.

## 4. Флаги функций

**Локальные флаги без сети:** значения по умолчанию — в коде (`defaults.ts`); переопределения — в `app_setting` (`flags.overrides`), скрытый способ включить — dev-режим/файл. Публичный реестр типизирован: `flags.aiChat`, `flags.reports.aiSection`, `flags.advancedMode`, пост-MVP `flags.reminders`.

**Почему не удалённые флаги (LaunchDarkly/Unleash):** сетевой трафик без пользы пользователя (против FR-7.3), а тумблеры «на лету» для десктоп-релизов малой ценности — фича всё равно едет в обновлении. **Компромисс:** бета-канал (10 §2) выполняет роль постепенного включения.

## 5. Конфигурация

Слои (от низкого к высокому приоритету): встроенные дефолты → `app_setting` (настройки пользователя) → переменные окружения (только dev/CI). Валидация всех слоёв — zod-схема при старте; невалидная конфигурация = падение при старте с понятной ошибкой, не «тихие дефолты».

Секретов в конфигурации нет по конструкции (ключи — в ОС-хранилище, 08 §2). Пути — только через `app.getPath()` (userData, logs, downloads) — переносимость и предсказуемость бэкапов.

## 6. Управление окружениями

| Окружение | Признак | Изоляция |
|---|---|---|
| dev | `!app.isPackaged` | отдельный userData (`health-log-dev`), горячая перезагрузка, mock-часы опционально |
| test/CI | `HEALTH_LOG_ENV=test` | temp-директории, in-memory/TMP SQLite, фейковые порты (Clock, LlmEngine, Egress) |
| prod | packaged | реальный userData; всё продуктовое |

**Почему жёсткая изоляция dev/prod данных:** одна опечатка в dev не должна стереть чей-то дневник; дешёвая страховка.

## 7. Логирование

- **Pino → ротируемые файлы** в userData/logs (категории: app, ipc, db, ai, net, job). Уровни: debug в dev, info в prod, trace — по флагу диагностики.
- **Редакция PHI на уровне логгера:** сериализатор удаляет значения измерений, заметки и содержимое чата — логируются типы операций, id, длительности, коды ошибок (NFR-12). Проверяется тестом-контрактом логгера.
- Диагностический пакет (NFR-12): по явному действию — zip логов + версий + health-статусов без PHI; пользователь видит содержимое перед отправкой (обычно — в issue).

## 8. Мониторинг (без телеметрии, D12)

Внешнего мониторинга нет — по SRS (FR-7.2). Внутренняя наблюдаемость:

- **Self-check при старте:** целостность БД, наличие ключа, версия схемы, состояние воркера → экран «О приложении»/диагностика.
- **Локальные метрики здоровья:** время старта, длительность генераций, ошибки по категориям — агрегаты в `app_event`, видны в диагпакете.
- **Крэш-отчёты:** локально (main/renderer/worker), без автоотправки; опциональная отправка с копией — будущее, только с явным согласием (OQ).
- **Продуктовые метрики:** скачивания релизов (GitHub), опросы, интервью — вне приложения (SRS BG-2, A-11).

## 9. Аналитика (продуктовая, локальная)

`app_event` — журнал локальных событий (`screen_view`, `measurement_added` (только длительность), `summary_generated` (модель, длительность, отменена), `export_created` (формат), `error` (только код)). Назначение: диагпакет для поддержки и локальный ответ на вопрос «пользовались ли фичей» при интервью пользователя. **Не отправляется никогда.**

## 10. Обработка ошибок (сквозная)

- **Домен/application:** `Result<T, AppError>` — исключения не пересекают границы слоёв; `AppError{code, i18nKey, params, cause}`.
- **IPC:** маппинг в `AppErrorDto` (05 §2); неожиданные исключения ловятся на границе → `APP/INTERNAL` + локальный лог с cause.
- **Глобальные хендлеры:** main (`process.on('uncaughtException')` → лог + безопасное сохранение состояния + диалог), renderer (ErrorBoundary, 06 §9), worker (краш → перезапуск процесса).
- **Таксономия кодов:** `MEASUREMENT/*`, `STORAGE/*` (CORRUPT, MIGRATION_FAILED), `AI/*` (MODEL_MISSING, GENERATION_CANCELLED, GUARDRAIL_REFUSAL), `NET/*` (BLOCKED_BY_POLICY, DOWNLOAD_FAILED), `VAULT/*` (LOCKED, WRONG_PASSPHRASE), `APP/INTERNAL`.
- **Кризисные состояния:** повреждение БД/провал миграции → полноэкранное восстановление (выбор копии), блокировка прочего UI (EC-14) — единственное место с «техническим» текстом, раскрываемым по явному действию.

## 11. Офлайн-стратегия

Приложение **не имеет online-режима по умолчанию**: все функции локальны. Сетевые операции описываются машиной состояний `idle → checking/downloading → done/failed/paused` с докачкой и явным повтором; неудача сети никогда не блокирует журналирование/статистику/экспорт. Индикатор сетевой активности — в экране «Приватность» в реальном времени (`net:activity`). Будущая синхронизация (пост-MVP) — отдельный модуль с собственным ADR; архитектурных заложенных ожиданий «сеть появится» нет.
