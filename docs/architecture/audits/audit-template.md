# Сетевой аудит релизной сборки — шаблон отчёта (AC-4.1)

**Статус:** действующая процедура · TASK-106 · реализует AC-4.1 (BG-2), FR-7.1/7.3

---

## 1. Назначение

Центральное доказательство обещания BG-2 («данные не покидают устройство без вашего
согласия») перед каждым публичным релизом: запуск **релизной сборки** с фиксацией
ВСЕХ сетевых соединений ОС в сценариях S1–S4, сверка наблюдаемого с журналом
приложения, вердикт PASS/FAIL. Отчёт (заполненная копия этого шаблона) прикладывается
к каждому релизу; расхождение «журнал ↔ факт» — блокер релиза (карта: T-7.1.3).

Проверка на уровне ОС ловит и «скрытые» соединения зависимостей, которые код-ревью
и линтер не увидят. Сама процедура без внедрения трафика (только наблюдение);
артефакты содержат только метаданные соединений (ip:port, state, время) — содержимого
TLS нет, прикладывать к отчёту безопасно (§14 спеки).

## 2. Инструменты и принципы

- **Скрипт-сборщик:** `node tools/scripts/net-audit.mjs --scenario <S1|S2|S3|S4>`
  — polling `Get-NetTCPConnection` каждые 500 мс (Windows-native, без установки;
  альтернатива `netsh trace` не требуется), pid-фильтр по процессам приложения,
  reverse-dns, дедуп, timeline (`timeline-S<N>.md`) + raw-лог (`connections-raw.jsonl`).
  Скрипт — сборщик данных: вердикт и сверка журнала — за оператором по этому шаблону
  (авто-дифф журнал↔наблюдения — будущая работа §5).
- **Опционально:** Fiddler/proxy для содержимого HTTPS-сигнатур (SNI) — качественный
  мониторинг содержимого скриптом невозможен, поэтому прогон в CI не автоматизирован
  (§5 «Не включено»).
- **Ограничение полноты:** 500-мс polling ловит секундные соединения (updater-сессии
  живут секунды —TASK-096); теоретические sub-500-мс звонки между тиками —
  остаточный риск, документируется в вердикте. Вторая линия защиты — depcruise-запрет
  прямых `net`/`fetch` вне EgressGateway (CONTRIBUTING §6.4) + сам gateway.

## 3. Заявленные хосты (белый список)

Единственный источник сетевых операций — EgressPolicy
(`apps/desktop/src/main/modules/platform-services/egress/egress-policy.ts`): две
операции, каждая за согласием пользователя.

| Операция          | Заявленный хост                        | Источник                                                                    |
| ----------------- | -------------------------------------- | --------------------------------------------------------------------------- |
| `updates.check`   | `github.com`                           | generic-фид поверх GitHub Releases (`apps/desktop/electron-builder.yml` → publish.url) |
| `models.download` | `huggingface.co` (хост URL манифеста)  | `apps/desktop/resources/models-manifest.json` → descriptor.url               |

**Допуск по CDN (зафиксировано, §13 спеки):** соединение на уровне ОС может идти
на IP до nslookup/DNS-reverse — reverse-dns может резолвить CDN-имя, не совпадающее
с заявленным хостом. Допуск: редиректы загрузки на CDN того же владельца —
`objects.githubusercontent.com` (активы GitHub Releases) и `*.huggingface.co`,
`cas-bridge.xethub.hf.co`/`cdn-lfs*.huggingface.co` (файлы моделей Hugging Face).
Иное имя или IP без PTR — кандидат в FAIL: сверить вручную (whois/проба загрузки)
и зафиксировать объяснение в вердикте.

**Оговорка updater-байтов (TASK-096 §22):** трафик updater'а выполняет electron-updater
вне gateway — журнал фиксирует факт и статус проверки, байты приблизительные/нулевые.
Сверка S3 ведётся по факту проверки, не по байтам.

**Оговорка blocked-записей:** gateway пишет blocked-запись, когда запрос достигает
его без согласия; в текущей сборке UI перехватывает попытки ДО gateway
(UpdatesSection §13 — подсказка вместо вызова; ModelCard §13 — согласие-диалог
вместо вызова), поэтому при попытках без согласий blocked-записей в журнале НЕТ —
это штатное поведение (defense-in-depth: gateway-путь blocked покрыт интеграционными
тестами `egress-gateway.int.test.ts`). FAIL-критерий §13 трактуется так: попытка без
согласия обязана НЕ произвести ни сетевой активности, ни ok/running-записей в журнале.

## 4. Подготовка

1. Релизная сборка: `pnpm dist` (установщик) либо win-unpacked; зафиксировать в
   отчёте: версия приложения, коммит/тег исходников, подпись (если есть).
2. Чистый профиль: свежая установка (S1 начинается с чистого user-data).
3. Запуск скрипта ПЕРЕД запуском приложения (монитор ждёт процессы ≤60 с):

   ```bash
   node tools/scripts/net-audit.mjs --scenario S1 --duration 330
   # интерактив: Enter — отметить шаг чек-листа выполненным, q — завершить;
   # без терминала — --duration <sec>; имена процессов — --exe "Health Log"
   ```

4. Артефакты прогона: `tools/audit-results/<дата>-<S>/` (gitignored — в репо не
   входят; в отчёт включаются выдержки и скриншоты). Отчёт коммитится в
   `docs/architecture/audits/` (история доказательств по релизам, §18).

## 5. Сценарии

Каждый сценарий — отдельный прогон скрипта (или последовательные окна одним сеансом
приложения, как в первом отчёте 2026-Q1). Шаги выполняет оператор вручную.

### S1 — чистая установка, согласий нет → ожидание: 0 соединений

1. Установить/запустить релизную сборку с ЧИСТЫМ профилем.
2. Убедиться: секция «Приватность» — оба согласия выключены.
3. Работать ~5 минут полным функционалом кроме сети (измерения, история,
   динамика, отчёты, экспорт, настройки).
4. Убедиться: timeline — 0 соединений; журнал сети — записей нет.
5. **Скриншот-доказательство** (ключевой результат): экран «Приватность» с пустой
   лентой → `assets/`.

### S2 — согласие моделей → скачать модель → ожидание: только хост манифеста

1. «Настройки → Приватность»: включить «Загрузка моделей ИИ» (или согласие-диалог
   из карточки модели — тот же эффект).
2. «ИИ → Модель»: скачать модель из манифеста (Llama 3.2 1B Instruct, ~800 МБ).
3. Дождаться состояния installed (sha256 проверяется приложением).
4. Убедиться: в timeline — только `huggingface.co` и его CDN-редиректы (допуск §3);
   в журнале — `models.download` c байтами.

### S3 — согласие обновлений → проверить → ожидание: только github.com/api

1. «Настройки → Приватность»: включить «Проверка обновлений».
2. «Настройки → Обновления»: «Проверить обновления»; дождаться результата
   (в т.ч. «нет обновлений»/ошибка фида — проверка состоялась).
3. Убедиться: в timeline — только `github.com` (и CDN-допуск §3); в журнале —
   `updates.check` (байты updater'а — см. оговорку §3).

### S4 — отзыв согласий → повтор → ожидание: 0 соединений

1. «Настройки → Приватность»: отозвать ОБА согласия (диалог подтверждения).
2. Повторить попытку скачивания модели → ожидание: согласие-диалог UI (перехват),
   сети нет.
3. Повторить «Проверить обновления» → ожидание: подсказка UI (перехват), сети нет.
4. Убедиться: timeline — 0 соединений; журнал — нет новых ok/running-записей
   (blocked-записи — см. оговорку §3).

## 6. Сверка «журнал ↔ наблюдения»

Источник журнала: экран «Приватность» (живая лента — скриншот) или выгрузка
диагпакета «Настройки → Диагностика» (файл `network-journal.json` внутри zip).
Правило (§2 цели): **каждое** наблюдение скрипта имеет запись в журнале приложения,
и **каждая** сетевая запись журнала имеет наблюдаемое соединение (в пределах
допусков: updater-байты §3, CDN-имена §3). Сверка выполняется глазами по таблице
ниже; дрейф в любую сторону — FAIL (блокер релиза).

| Наблюдение (timeline) | Хост после допуска §3 | Запись журнала (op/статус/байты) | Совпало? |
| --------------------- | --------------------- | -------------------------------- | -------- |

## 7. Критерии FAIL (§13 спеки)

- [ ] Любое соединение вне заявленных хостов (с учётом допуска §3) в любом сценарии.
- [ ] Расхождение «наблюдаемо, но журнала нет» (кроме оговорок §3).
- [ ] Попытка без согласия произвела сетевую активность или ok/running-запись
      в журнале (gateway/перехват не сработали).

Любой отмеченный пункт — блокер релиза: расследование до выпуска или строка
в реестре отложенных с обоснованием.
