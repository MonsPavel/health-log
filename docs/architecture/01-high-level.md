## 1. Общая форма системы

Health Log — **локальное десктоп-приложение без собственных серверов**. Все данные, вычисления и ИИ-инференс — на машине пользователя. Единственные внешние точки: сервер обновлений и реестр моделей, оба — только по явному действию пользователя (SRS FR-7.3).

## 2. D1: рантайм — Electron + React + TypeScript

**Почему.** (1) Стек задан владельцем продукта: JS + React. (2) Node-экосистема даёт зрелые биндинги и к SQLite (better-sqlite3), и к llama.cpp (node-llama-cpp) — обе критичные интеграции остаются в одном языке. (3) Bus-factor (SRS R-8): один мейнтейнер быстрее итерирует в одном стеке. (4) Упаковка/подпись/автообновление Windows — отработанные механизмы.

**Альтернативы.**
- *Tauri 2 (Rust-ядро + React):* установщик ~15 МБ против ~85 МБ, меньше RAM. Но: ядро на Rust при команде из одного JS-разработчика — прямой удар по R-8; LLM всё равно потребовал бы llama.cpp-сайдкар; WebView2 — внешняя зависимость на Windows.
- *NW.js / Neutralino:* слабее экосистема и инструментарий безопасности.
- *Чисто веб-приложение:* не выполняет требования локального хранилища с шифрованием и локального LLM.
- *Qt / .NET MAUI:* нарушение стека.

**Компромиссы.** RAM/диск тяжелее (главный риск против NFR-5 и лимита установки ≤200 МБ без модели — на верхней границе; см. D1a). Смягчение: ленивые загрузки, вынос тяжёлых задач из главного процесса. **Путь отхода:** домен, приложение и контракты вынесены в независимые от Electron пакеты — рендерер и слои переносимы на Tauri без переписывания логики, если лимиты будут нарушены.

**D1a (следствие).** Размер установки — контролируемый бюджет сборки (10 §): tree-shaking, asar, без dev-зависимостей, лимит проверяется в CI. Превышение 200 МБ = красный билд.

## 3. «Бэкенд» в локальном приложении

Запрошенный раздел «Backend Architecture» отображается на **главный процесс Electron**: он содержит все слои Clean Architecture (domain → application → adapters), композицию зависимостей, фоновые задачи и работу с файлами. Рендерер — тонкий клиент, не имеющий доступа к Node и БД; он общается только через IPC-контракт (05).

**Почему так.** SRS запрещает облако (FR-7.2, non-goals); «бэкенд как сервер» в системе отсутствует по продуктовым причинам, а не по недосмотру. Любая будущая серверная часть (пост-MVP синхронизация, OQ) появится как отдельный сервис **за тем же IPC-подобным контрактом**, что не потребует переделки UI.

**Альтернатива:** допускать прямой доступ рендерера к БД через preload — быстрее в разработке, но ломает модель безопасности (рендерер исполняет веб-контент и должен считаться недоверенным; см. 08 §4) и усложняет тестирование логики.

## 4. D2: модульный монолит, а не микросервисы

**Почему.** Один пользователь, одна машина, одно хранилище, одна точка развёртывания. Микросервисы дали бы сетевые сбои, протоколы и операционную сложность без единой выгоды. Модульность достигается границами внутри процесса: каждый ограниченный контекст (02) — самодостаточный модуль с публичным API и запретом импорта чужих внутренностей; правила проверяются инструментами в CI (dependency-cruiser, 03 §5).

**Альтернативы.** (1) Слои без модулей («большой шар» domain/application/adapters) — быстрее старт, но связность падает при росте и vision health-log (второй-третий тип показателей) превратит расширение в распутывание. (2) Микросервисы/отдельные процессы на контекст — не обоснованы (см. выше); единственный выделенный процесс — LLM-воркер (D5), и он выделен по причине изоляции сбоев/памяти, а не «сервисности».

**Компромиссы.** Модульные границы в монолите дисциплинируют только при механической проверке — поэтому правила границ — это код в CI, а не конвенция. При появлении облачной синхронизации один-два модуля (data-care, platform-services) станут кандидатами на выделение — границы спроектированы под это.

## 5. Поток событий (обзор)

Два механизма, каждый для своей задачи:

1. **Запрос–ответ (команды/запросы):** UI → IPC-хендлер → use case (application) → домен/адаптеры → результат → UI. Единственный путь мутаций.
2. **Событийная шина (главный процесс):** use case публикует доменные события (`measurement:changed`, `data:versionBumped`, `ai:token`, `lock:engaged`, `net:activity`, `update:available`); подписчики — инвалидация кэшей UI (broadcast в рендерер), обновление бейджа «данные изменились» (FR-5.7, через счётчик `data_version`), журнал сетевой активности (FR-7.1).

Подробные последовательности: 05 §4 (IPC), 07 §5 (ИИ-поток и стейлс).

## 6. Сторонние интеграции (полный список)

| Интеграция | Назначение | Гейт |
|---|---|---|
| GitHub Releases | проверка/загрузка обновлений приложения | opt-in при первом запуске (NFR-11), через EgressGateway |
| Реестр моделей (HuggingFace / GitHub LFS) | скачивание LLM | явное действие пользователя, манифест + sha256 (07 §6) |
| Системное хранилище ключей (DPAPI/Keychain) | защита ключа шифрования | локально, без сети |
| ОС-уведомления | пост-MVP напоминания | локально |
| Будущее: BLE-тонометры, файлы Apple Health/Google Fit, печать | FR-12 | пост-MVP/future, через те же порты адаптеров |

Принцип: **никаких сторонних SDK в рендерере**; каждая интеграция — адаптер за портом в своём модуле, сеть — только через EgressGateway (08 §5).

## 7. Ключевые потоки данных (обзор; детали в профильных файлах)

- **Запись измерения:** форма → IPC `measurements/add` → валидация (домен) → репозиторий (SQLite, транзакция, +1 `data_version`) → событие `measurement:changed` → UI обновляет кэш; статистика пересчитывается по требованию.
- **Чтение статистики:** UI → `stats/period` → read model (SQL-агрегаты) → чистые функции аналитики (классификация по шкале) → UI. Без побочных эффектов, детерминировано (NFR-10).
- **ИИ-резюме:** UI → `ai/summary/generate(period)` → сборка контекста (детерминированная проекция данных + политика) → LLM-воркер → стрим токенов в UI → сохранение резюме + `context_hash` → повторный запрос с тем же хешом отдаётся из кэша (07 §5).
- **Экспорт/копия:** `report/pdf` → read model → рендер PDF в рабочем пуле → файл в выбранное пользователем место. Данные пользователя наружу не передаются никогда.

## 8. Офлайн-позиция

Система спроектирована как **«всегда офлайн»**: сеть — не деградировавший режим, а исключение по явному запросу. Все экраны полностью функциональны без сети; сетевые операции (обновление, модель) имеют явные состояния (idle/checking/downloading/failed/paused) и докачку. Отдельная «offline strategy» как стратегия синхронизации отсутствует — синхронизируться не с чем; при будущей облачной синхронизации вопрос конфликтов будет решаться отдельно (последовательная запись одного пользователя упрощает задачу до LWW с журналом).
