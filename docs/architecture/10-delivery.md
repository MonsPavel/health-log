# 10. Доставка: тестирование, CI/CD, развёртывание

**Статус:** черновик v0.1 · 2026-09-24

---

## 1. Архитектура тестирования

Пирамида, смещённая в чистые слои (следствие Clean Architecture):

| Уровень | Что тестируется | Инструмент | Гейт |
|---|---|---|---|
| **Юниты домена** | сущности, VO, инварианты, `Classifier`, `TypoHeuristic`, `GuardrailPolicy` | Vitest + **fast-check** (property-based: например, «любые sys<dia отклоняются») + **реперные медицинские примеры** (golden fixtures) | покрытие domain ≥90% (NFR-10) |
| **Юниты application** | use case'ы с фейками портов (in-memory repo, фейковые Clock/LlmEngine) | Vitest | покрытие application ≥85% |
| **Интеграции** | реальные SQLite-репозитории (temp-файл), миграции, крипто-контур (ключ→копия→восстановление), FTS, транзакции + **тест отключения процесса в момент записи** (NFR-3) | Vitest, временные каталоги | обязательны |
| **Контракты IPC** | соответствие хендлеров zod-схемам contracts; события | Vitest над схемами | обязательны |
| **E2E** | пути UC-01, UC-05, UC-07, AC-7 (a11y axe-core, крупный текст), старт/ошибки | **Playwright `_electron`**, Windows-раннер | smoke на каждый PR, полный набор — на тег |
| **AI-оценки** | «красный набор» (AC-5.1) на компактной модели ночью; полная модель перед релизом | tools/eval, детерминированные проверки формы ответа | гейт релиза |
| **Производительность** | старт ≤3 c, график 10k точек <1 c, PDF <30 c (NFR-4) | bench-скрипты, run на теге | отчёт; порог — предупреждение |
| **Архитектура** | правила зависимостей (03 §4), лимит размера установки ≤200 МБ | dependency-cruiser, скрипт аудита размера | ошибка сборки при нарушении |

**Почему так.** Тестирование домена без Electron/SQLite/LLM даёт миллисекундный цикл и стабильность; интеграционные тесты бьют именно по рискам SRS (потеря данных R-4, крипто R-9); E2E держит минимальным — хрупко и медленно. **Компромисс:** AI-оценки не полностью автоматизируемы (семантика) — формы ответа проверяет CI, семантику — ручной золотой набор (07 §7).

## 2. Стратегия развёртывания

Дистрибуция — **без серверов**: GitHub Releases как канал артефактов.

- **Каналы:** `latest` (стабильный) и `beta` (ранний доступ, роль постепенного включения фич вместо удалённых флагов, 09 §4).
- **Артефакты:** подписанный NSIS-установщик Windows (x64); позже — macOS (Developer ID, notarization) и Linux (AppImage/deb). Portable-сборка — post-MVP (C).
- **Обновления:** electron-updater, провайдер — GitHub Releases; **проверка обновлений только при выданном согласии** (FR-7.3, NFR-11, состояние видно в журнале приватности). Установка — с подтверждением пользователя.
- **Модели:** вне установщика; реестр-манифест (07 §6) в отдельном репозитории/HLFS; обновление манифеста не требует релиза приложения.
- **Откат:** установка предыдущей версии; миграции БД вперёд-только, но каждая миграция предварена автокопией (04 §5) → возврат на старую версию = восстановление копии. Это документируется в release notes.

**Deployment Architecture:**

```
┌ Разработка/CI ────────────────┐      ┌ Каналы ──────────────┐     ┌ Машина пользователя ─────────────┐
│ GitHub Actions (win runner)   │      │ GitHub Releases      │     │ Electron app (main+renderer+worker)│
│ build → sign → package → e2e  │ ───▶ │  latest / beta       │ ──▶ │ userData: БД(SQLCipher), модели,   │
│ → draft release + manifest    │      │  модели (HLFS/HF)    │     │ ключи (ОС-хранилище), логи, копии  │
└───────────────────────────────┘      └──────────────────────┘     └───────────────────────────────────┘
```

**Почему не авто-обновление по умолчанию / не свой update-сервер:** любой фоновый трафик подрывает BG-2; собственный сервер — операционная нагрузка без выгоды на текущем масштабе (R-8). **Компромисс:** распространение через GitHub ограничивает аудиторию без аккаунта GitHub — приемлемо для MVP, переезд на собственный CDN не затрагивает архитектуру приложения (только конфиг провайдера).

## 3. CI/CD (GitHub Actions)

**PR:** lint + typecheck → юниты/интеграции/контракты → dependency-cruiser (границы) → сборка + аудит размера → Playwright smoke (Electron) → превью-артефакт.
**Merge в main:** всё выше + полный E2E на Windows; зелёный main = всегда собираемый продукт.
**Тег `v*`:** матричная сборка → подпись (секрет сертификата) → пакетирование → полный E2E + AI-оценки (компактная модель) + perf-бенч → draft release с артефактами, манифестом моделей и release notes → публикация вручную (кнопка мейнтейнера).
**Nightly:** AI-оценки + bench; отчёты в артефактах CI.

Кэш: pnpm store, кэш Electron-бинарей и rebuilt-нативных модулей. Секреты: сертификат подписи, токен публикации — в GitHub Secrets.

**Почему пайплайн «сборка-на-тег» а не деплой-на-merge:** релиз десктопа — это подписанный артефакт, а не выкладка на сервер; человек публикует релиз (последняя ручная точка контроля перед пользователями).

## 4. Критерии качества релиза (связка с SRS DoD)

1. Все гейты таблицы §1 зелёные на целевых ОС.
2. «Красный набор» ИИ — пройден на каждой модели, заявленной в манифесте релиза (AC-5.1).
3. Сетевой аудит релизной сборки: трафик только из белого списка при включённых согласиях (AC-4.1).
4. Тест потери питания: ноль потерянных сохранённых записей (NFR-3).
5. Размер установки ≤200 МБ без модели (NFR-5, D1a).
6. Реперные примеры статистики совпадают (NFR-10); версии приложения/шкал/моделей отображаются («О приложении»).
