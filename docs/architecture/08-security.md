# 08. Модель безопасности

**Статус:** черновик v0.1 · 2026-09-24 · реализует FR-7, NFR-1/2, EC-14

---

## 1. Позиционирование угроз

Продукт — локальное хранилище специальных категорий данных (здоровье). Границы доверия:

```
┌─ Доверенная зона ───────────────────────────────────────────┐
│ main-процесс (Node), llm-worker, ОС-хранилище ключей, файлы │
└──────────────▲──────────────────────────────────────────────┘
               │ IPC-контракт: валидация zod на каждом вызове
┌──────────────┴──────────────────────────────────────────────┐
│ renderer = НЕдоверенный (исполняет веб-контент)             │
└─────────────────────────────────────────────────────────────┘
Внешняя сеть: только EgressGateway, только белый список (§5)
```

## 2. Аутентификация (локальная)

Аккаунтов нет (SRS A-7): аутентифицируется **доступ к данным**, не пользователь.

**Ключ БД (32 байта, случайный, при первой установке):**
- *Профиль по умолчанию (без пароля):* ключ обёрнут Electron `safeStorage` (Windows DPAPI / macOS Keychain / libsecret) и хранится в userData. Разблокировка — автоматически при входе пользователя в ОС.
- *С паролем (FR-7.5):* ключ обёрнут двойно — `KEK = Argon2id(passphrase, salt)`; разблокировка требует пароля; экран блокировки + авто-блок по простою; rate-limit попыток (экспоненциальная задержка). Забытый пароль = данные невосстановимы — предупреждение при включении (NFR-2).

**Почему safeStorage, а не свой DPAPI-P/Invoke или keytar:** встроенный API Electron, поддержка трёх ОС, без устаревших зависимостей. **Почему Argon2id:** стойкий KDF против офлайн-перебора; параметры — memory-hard по рекомендациям OWASP.

## 3. Авторизация

Модель — **одна машина, один активный профиль (MVP)**. Авторизация реализуется не в UI, а в репозиториях: **каждый запрос данных обязан нести `profileId`, полученный из сессии main-процесса**, а не из рендерера (UI не может запросить «чужой» профиль — параметра нет в контракте). Пост-MVP мультипрофильность (FR-11) расширяет это в переключатель сессий с полной изоляцией.

**Почему не «спрятать чужие данные в UI»:** доверять границе нельзя по определению; принудительный скоуп в репозитории — единственная точка, которую нельзя обойти из рендерера.

## 4. Укрепление Electron

- `contextIsolation: true`, `sandbox: true`, `nodeIntegration: false`; preload — только `contextBridge` с контрактным клиентом.
- Валидация всех IPC-полезных нагрузок zod-схемами **до** вызова use case (рендерер недоверенный).
- CSP в рендерере: без remote-источников; никаких удалённых URL в `<webview>`/iframe; внешние ссылки — через системный браузер после явного клика.
- Отключение навигации окна на внешние протоколы; single-instance lock (EC-24).

## 5. Сетевая политика — EgressGateway (D11, FR-7.1/7.3)

Единственная точка сети приложения. Все адаптеры (updates, model store) обязаны идти через неё; прямые `fetch`/`net` вне гейтвея запрещены линтером.

```
EgressGateway.request(op):
   1. op ∈ EgressPolicy.allowlist?          (updates.check | models.download)
   2. consent(op) == granted?               (настройки/первый запуск)
   3. журнал: network_event(kind, endpoint, status, bytes)
   4. выполнить; по завершении — обновить запись журнала
Отказ (вне списка / нет согласия) → AppError 'NET/BLOCKED_BY_POLICY' — видимый, не тихий.
```

**Почему центрально:** аудит AC-4.1 должен быть возможен одной проверкой кода, а не обходом всех вызовов; журнал FR-7.1 автоматически полон. **Компромисс:** дисциплина разработки («сеть только через гейтвей») поддерживается правилом линтера и код-ревью.

## 6. Модель угроз (сводка)

| Угроза | Контроль |
|---|---|
| Кража файла БД с диска | SQLCipher + ключ в ОС-хранилище/пароль (§2); -wal удаляется при закрытии |
| Локальный доступ к работающей машине | Опциональный пароль + авто-блок (FR-7.5); это защита от «подошёл и посмотрел», не от форензики — честно в документации |
| Компрометация рендерера (XSS в веб-контенте) | Sandbox + CSP + отсутствие Node-доступа; максимум, что получит атакующий — IPC-клиент с валидируемыми вызовами |
| Вредоносная модель (подмена/отравление) | Манифест + sha256 (07 §6); модель исполняется в изолированном воркере без доступа к ключам и файлам пользователя |
| Prompt-инъекция через заметки | Заметки = данные в контексте; у LLM нет инструментов/сети; post-фильтр (07 §4) |
| MITM при загрузке обновлений/модели | TLS + подпись обновлений (electron-updater, NFR-11) + sha256 моделей |
| supply-chain (зависимости) | lockfile, `npm audit`/`pnpm audit` в CI, минимум нативных зависимостей, pinned-версии |
| Остаточные данные после «удалить всё» | Wipe: db/-wal/-shm, файлы ключей, логи, события (FR-6.5); предупреждение об ограничениях файловой системы в документации |
| Логи как канал утечки | Редакция PHI в логгере (09 §7): значения измерений и заметки не логируются никогда |

## 7. Крипто-инвентарь

| Назначение | Алгоритм/механизм |
|---|---|
| Шифрование БД | SQLCipher (AES-256) |
| Обёртка ключа без пароля | Electron safeStorage (DPAPI/Keychain) |
| Обёртка ключа с паролем | Argon2id → AES-256-GCM KEK |
| Целостность копий/моделей | SHA-256 (+ подпись манифеста моделей) |
| Подпись установщиков/обновлений | Authenticode (Windows) / Developer ID (macOS) |

Своей криптографии в проекте нет — только стандартные примитивы из проверенных библиотек/ОС.
