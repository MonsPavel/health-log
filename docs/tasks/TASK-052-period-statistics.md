## 2. Цель

Единая read model статистики периода: количество; avg/min/max/SD (СДА, ДДА, ЧСС); средние утро/вечер и разница; пометка критических значений за период; регулярность (дней с измерениями, longest streak); флаг «мало данных». Детерминированная, покрытая golden-фикстурами (NFR-10).

## 3. Бизнес-контекст

Это контракт трёх потребителей сразу: дашборд (TASK-061), PDF-отчёт врачу (TASK-068) и ИИ-контекст (TASK-083). Ошибка в среднем за период — подрыв клинического доверия (NFR-10), поэтому вычисления — чистые функции над сырыми точками с эталонными тестами, а не SQL-агрегаты без проверки.

## 4. Технический контекст

- **Архитектура:** read models контекста Analytics — арх. 02 §3.2, 03 §2; чистые функции — 02 §5.
- **Модуль:** `analytics/{domain,application}`.
- **Обоснование:** гибрид: SELECT достаёт сырые точки (минимум SQL-логики), вычисления — чистый TS (тестируемость, отсутствие SQL-диалектной математики SD); на 50k записей по 10k за период — десятки мс (TD-8: без инкрементальных кэшей). SD — выборочное (sample, n−1): зафиксировано, n<2 → SD undefined.

## 5. Объём

- **Включено:** запрос точек периода (порт measurement.listByPeriod — уже есть; без новых SQL); доменные чистые функции: `mean/min/max/sampleSd`, `splitByDayPart` (константы: утро 06:00–11:59, вечер 18:00–23:59, иначе 'other' — по настенному времени Instant), `difference(morning, evening)`, `criticalPeriodFlag` (были ли high/low — политика TASK-020 по точкам), `regularity` (уникальные настенные дни, longest streak дней ПОДРЯД — включая сегодня? правило: streak дней с измерениями до последнего дня с измерением, без штрафов за старые пропуски FR-4.4); сборка `PeriodStatistics`-структуры (§7); фикстуры: генератор детерминированных периодов + ручные эталоны (5 наборов); property-тесты; coverage-гейт домена 90% включается (vitest thresholds для analytics/domain).
- **Не включено:** классификация средних (TASK-053 — получает готовые avg), каналы (TASK-054), распределение по категориям (нужен классификатор — поле структуры появля‹ется в TASK-053 заполнением, место зарезервировано).
- **Будущая работа:** инкрементальные агрегаты (TD-8), медиана (при запросах).

## 13. Бизнес-логика

Ключевые правила: part-stats только при ≥1 измерении в части (иначе undefined — UI не показывает пустые части); delta — evening.avg − morning.avg по каждому из СДА/ДДА, только если обе части есть; regularity дни — по настенной дате (EC-06 согласовано с TASK-033); streak: максимум подряд идущих дней с ≥1 измерением внутри периода (не «до сегодня» — период замкнут); SD выборочное, при n=1 → undefined. Пограничные: ночные измерения 00:15 → 'other' (не «вчера-вечер»); запись ровно 06:00 → утро; 11:59:59 → утро; 12:00 → other.

## 19. Стратегия тестирования

Golden-фикстуры (5 периодов, ручные эталоны): (a) классический 30 дней 4/день; (b) только утренние; (c) разрыв 14 дней посреди; (d) 3 записи (мало данных — оба true); (e) критические значения внутри. Свойства: перестановка записей не меняет агрегаты (кроме streak? streak тоже порядок-инвариантен); добавление записи не уменьшает count/дни; SD NaN-свобода. Точность: округление до 1 знака фиксируется эталонами.

## 20. Критерии приёмки

- [ ] 5 golden-фикстур зелёные (все поля §7, включая undefined-ветки).
- [ ] Пустой период → count=0, все части undefined, insufficientData оба true, БЕЗ NaN (тест).
- [ ] Границы day-part: 05:59→other, 06:00→morning, 11:59→morning, 12:00→other, 18:00→evening, 23:59→evening (таблица тестов).
