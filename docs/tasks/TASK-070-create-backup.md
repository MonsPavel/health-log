## 2. Цель

`CreateBackup`: консистентный снапшот БД (VACUUM INTO) во время работы приложения → AES-256-GCM контейнер (ключ из KeyVault) с манифестом `{formatVersion: 1, schemaVersion, appVersion, createdAtUtc, counts, sha256(db)}` → файл `.hlbackup`; подключение hook'а автокопии миграций (TASK-024) к этой же механике.

## 3. Бизнес-контекст

Страх №1 пользователя многолетнего дневника — потерять его (R-4): «умер ноутбук» (UC-08). Копия — один файл, зашифрованный (NFR-2: данные в покое шифрованы и в копии), проверяемый (sha256), переносимый.

## 4. Технический контекст

- **Архитектура:** Data Care — арх. 02 §3.5; копии зашифрованы — 08 §7; hook — TASK-024.
- **Модуль:** `data-care`.
- **Обоснование:** VACUUM INTO — консистентный снапшот без остановки записи (WAL): копия во время работы безопасна. Шифрование: AES-256-GCM на node:crypto, ключ — тот же keyHex БД (упрощение vs отдельный ключ: одна тайна у пользователя — решение задокументировано; компромисс: компрометация ключа = и БД и копии — приемлемо, ключ в ОС-хранилище). Формат контейнера: `[magic 'HLBK1'][manifest-json-len][manifest-json][ciphertext(db-файл)][auth-tag]` — простая линейная структура, версия в magic.

## 5. Объём

- **Включено:** use case `CreateBackup({targetPath|'ask'})`: (1) FileOpQueue; (2) VACUUM INTO во временный файл tmpdir; (3) sha256 снапшота; (4) манифест: formatVersion, schemaVersion (из meta), appVersion, createdAtUtc, counts (measurements по COUNT), dbSha256; (5) AES-256-GCM: iv 12б, cipher stream → контейнер (магия HLBK1 + manifest + ciphertext + tag); (6) запись через FileSaver (ask → диалог; автокопия-хук — во временный каталог без диалога); прогресс-события (фазы: snapshot/encrypt/write — coarse); cleanup tmp; коды: `BACKUP/FAILED`, `BACKUP/CANCELED`; подключение hook TASK-024: реализация интерфейса → createBackup во временный каталог (без диалога) перед миграцией; тесты roundtrip (до 071 — расшифровка в тесте тем же модулем): контейнер → расшифровать → БД открывается, данные равны.
- **Не включено:** восстановление (071), UI (073), расписание автокопий пользователю (074 — только подсказка; периодические АВТО-копии — пост-MVP: решение, только напоминание в MVP).
- **Будущая работа:** инкрементальные копии (не планируется — файл мал), несколько слотов копий.

## 8. База данных

VACUUM INTO требует ~2×места временно; снапшот содержит данные БЕЗ wal (checkpoint перед VACUUM? VACUUM INTO сам даёт консистентный снимок — wal не нужен). Открытие копии — только с ключом (он у пользователя в ОС-хранилище той машины! ОГРАНИЧЕНИЕ: копия без ключа на новой машине бесполезна → KeyVault-перенос? РЕШЕНИЕ-ПРОБЛЕМА: копия зашифрована ключом, ключ — DPAPI машины → на новом ПК копию не расшифровать! Решение: (а) пользователь экспортирует ключ? Сложно и небезопасно-гайд; (б) шифровать копию ПАРОЛЬ-производным ключом (Argon2id passphrase при создании копии — пользователь задаёт пароль копии) — независим от машины! ПРИНИМАЕТСЯ: пароль копии обязателен при создании (диалог в 073), KDF Argon2id, соль в манифесте. Обновление §2/§4: ключ копии = Argon2id(backupPassphrase) — не KeyVault. Compromise: пользователь может забыть пароль копии — предупреждение в UI 073 (как с паролем приложения NFR-2).)

## 13. Бизнес-логика

Кейсы: диск переполнен на фазе записи → BACKUP/FAILED + tmp cleanup (тест); отмена диалога → CANCELED; пароль копии: ≥8 символов политика (простая, предупреждение не блокировка); повторное создание — не запрещено (слоты не ограничиваем).

## 14. Безопасность

Argon2id параметры (как TASK-093 база); auth-tag GCM — целостность; sha256 манифеста сверяется при восстановлении (071); ключ копии никогда не логируется (redact). Пароль копии ≠ пароль приложения — независимы (документировать).

## 15. Производительность

50k БД (~20 МБ): VACUUM ~1–2 с, шифрование stream ~0.5 с — прогресс coarse достаточен.

## 19. Стратегия тестирования

Интеграционные (tmp): create→(расшифровка тестом через тот же crypto-модуль с паролем)→sqlite open снапшота→данные равны; битый контейнер (флип байта) → GCM-ошибка детектирована; диск-полный эмуляция (запись в /dev/full-подобный mock) → FAILED+cleanup; hook-миграции: тест миграции с реальным hook → файл pre-migration появился; пароль-политики.

## 20. Критерии приёмки

- [ ] Roundtrip: создать копию с паролем → расшифровать тестом → openEncrypted снапшота → записи равны исходной БД.
- [ ] Манифест: все поля §2, sha256 совпадает с расшифрованным файлом.
- [ ] Битый байт контейнера → ошибка целостности (GCM), не мусор-данные.
- [ ] Hook миграции TASK-024: перед миграцией создаётся pre-migration копия в userData/backups (интеграционный тест).
- [ ] Полный диск (мок) → BACKUP/FAILED, tmp-файлы удалены (тест-проверка каталога).
- [ ] Прогресс-события фаз доставлены (spy).
