## 2. Цель

Рабочий better-sqlite3 с поддержкой SQLCipher под Electron ABI: БД открывается только с ключом `PRAGMA key`; файл на диске нечитаем; пересборка автоматизирована скриптом и повторяема в CI/паковке.

## 3. Бизнес-контекст

NFR-2: шифрование включено по умолчанию без действий пользователя. Решение «шифровать сразу» (дорожная карта, фаза P1) — потому что перевод незашифрованной БД на шифрование позже = миграция данных и риск потери доверия. Это самый рискованный таск фазы — идёт первым в эпике, чтобы неопределённость вскрылась рано.

## 4. Технический контекст

- **Архитектура:** D4 — `docs/architecture/04-database.md` §1; безопасность — 08 §7 (крипто-инвентарь).
- **Пакеты:** `apps/desktop` (нативная зависимость), `tools/scripts`.
- **Обоснование (подтверждение арх.):** SQLCipher шифрует файл целиком (включая WAL) — прозрачнее и безопаснее шифрования полей. Путь получения: npm-пакет с prebuilt SQLCipher-сборкой better-sqlite3 для Electron (community-пресет) — **первичный вариант**; если пресет несовместим с текущим Electron — собрать из исходников (`better-sqlite3` build + SQLCipher через `npm_config_build_from_source`, связка openssl/csql) или **fallback-план Б**: обычный better-sqlite3 + шифрование файла БД целиком при закрытии (AES-GCM, ключ из KeyVault) — менее гранулярно, но рабоче; выбор фиксируется ADR-комментарием в скрипте сборки. Решение о пути принимается в этой задаче — это и есть её цель.

## 5. Объём

- **Включено:** скрипт `scripts/prepare-native.sh|.cmd`: установка совместимой версии better-sqlite3 (+SQLCipher), `electron-rebuild` при необходимости, проверка ABI; smoke-тест: создать БД с `PRAGMA key = "x'<hex>'"` и `PRAGMA cipher_*` дефолтами → вставить строку → закрыть → (а) открыть с ключом — данные читаются, (б) открыть без ключа/с неверным — ошибка; проверить, что первые байты файла ≠ SQLite-заголовок «SQLite format 3» (зашифрован); документ-заметка ADR в `docs/architecture/adr/0002-sqlcipher.md` (выбранный путь + альтернативы + компромиссы).
- **Не включено:** KeyVault (откуда ключ — TASK-023; здесь ключ генерируется в тесте), схема (TASK-025), интеграция с контейнером (TASK-027).
- **Будущая работа:** обновление SQLCipher-версии — только с тестом переоткрытия старой БД (compat).

## 6. Файлы

- **Создать:** `apps/desktop/scripts/prepare-native.*`, `apps/desktop/src/main/shared/db/sqlite.ts` (обёртка `openEncrypted(path, keyHex)` — `new Database(path)`, `PRAGMA key`, `PRAGMA foreign_keys=ON`, `PRAGMA journal_mode=WAL`), интеграционный тест `sqlite.int.test.ts` (tmp-каталог), `docs/architecture/adr/0002-sqlcipher.md`.
- **Изменить:** `apps/desktop/package.json` (postinstall → prepare-native), devDeps (electron-rebuild, prebuilt-пакет).

## 7. Модель предметной области

N/A. Контракт обёртки: `openEncrypted(path, keyHex): Database` — единственная точка открытия БД в проекте; ключ — hex 64 символа; ошибка неверного ключа пробрасывается как `STORAGE/BAD_KEY` (маппинг ошибки SQLCipher).

## 8. База данных

На этом шаге — только техническая БД-фикстура теста (одна таблица). Прагмы при открытии: `journal_mode=WAL`, `foreign_keys=ON`, `synchronous=NORMAL` (баланс durability/скорости; FULL не нужен — WAL+NORMAL переживает краш процесса, риск только при краше диска — принято, документировано в ADR).

## 13. Бизнес-логика

Критические случаи: неверный ключ → понятная ошибка `STORAGE/BAD_KEY` (не крипто-мусор в консоль); файл уже открыт другим процессом → SQLite-блокировка → `STORAGE/LOCKED` (защита — single-instance TASK-012, здесь только код ошибки); повреждённый файл → `STORAGE/CORRUPT` (детект — PRAGMA quick_check при старте, полный сценарий — TASK-100/101).

## 14. Безопасность

Ключ в памяти: hex-строка передаётся PRAGMA и обнуляется по возможности (JS-гарантий нет — документируется); ключ никогда не логируется (redact-список TASK-010 дополнить `keyHex`/`key`). Файл в tmp при тестах — удаляется в afterAll.

## 15. Производительность

Замер: 1000 вставок в транзакции на зашифрованной БД ≤1 с на dev-машине (фиксируется в ADR как базовая линия; порог NFR-4/9 проверяется в TASK-111). WAL обязателен — без него вставки в 10+ раз медленнее.

## 18. Телеметрия

Лог события открытия БД: путь (без имени пользователя — имя каталога может содержать! логировать только факт «db opened, cipher=on»), без ключа.

## 19. Стратегия тестирования

Интеграционный тест (tmp-каталог): create→insert→close→reopen с ключом→данные равны; reopen без ключа → ожидаемое исключение → маппинг STORAGE/BAD_KEY; первые 16 байт файла не равны SQLite-магии; WAL-файлы создаются. Тест пересборки: скрипт prepare-native выполняется и idempotentен (второй запуск — no-op, проверка хешем).

## 20. Критерии приёмки

- [ ] Интеграционный тест roundtrip с ключом зелёный (tmp-каталог).
- [ ] Открытие без ключа/с неверным → STORAGE/BAD_KEY (не сырая ошибка).
- [ ] Проверка первых байтов: заголовок «SQLite format 3» отсутствует (шифрование работает).
- [ ] `pnpm run prepare-native` идемпотентен; postinstall не ломает `pnpm install` на чистой машине.
- [ ] ADR-0002 записан: выбранный путь, альтернативы, компромиссы, производственная базовая линия.
- [ ] Замер 1000 вставок ≤1 с зафиксирован в ADR.
