## 2. Цель

Полный версионированный JSON-слепок: метаданные (`formatVersion`, appVersion, createdAt, counts), профили, все измерения, настройки (prefs), активные версии шкал; валидируемый собственной zod-схемой формата.

## 3. Бизнес-контекст

Мастер-формат — страховка от потери функциональности CSV и основа всех будущих миграций/интеграций (импорт пост-MVP, синхронизация) — данные, которые «понятны навсегда».

## 4. Технический контекст

- **Архитектура:** Reporting — арх. 02 §3.4; формат — версионированный контракт.
- **Обоснование:** zod-схема формата в `@hl/contracts` (мастер-формат — публичный контракт, экспорт обязан проходить валидацию собственной схемой — AC); `formatVersion: 1`; миграции формата — новые версии с сохранением чтения старых (правило в комментарии схемы).

## 5. Объём

- **Включено:** `packages/contracts/src/export/json-snapshot-schema.ts` (zod): корень `{formatVersion: 1, appVersion, createdAtUtc, counts: {measurements, profiles}, profiles: [{id, name, createdAtUtc}], measurements: [MeasurementDto…], prefs: Prefs|undefined, scales: [{code, version}]}`; use case `ExportJson(profileId)` — сборка слепка (замеры профилей, prefs из SettingsStore, активные шкалы из ScaleService) → `JSON.stringify(obj, null, 2)`; roundtrip-тесты (экспорт → zod.parse ok; все поля граничные: null-пульс, эмодзи, флаги).
- **Не включено:** импорт слепка (пост-MVP FR-6.6 — схема уже готова принять), логи/события в слепок (не данные пользователя — решение: только «контент»).
- **Будущая работа:** импорт с дедупликацией; include-опции (без prefs).

## 6. Файлы

- **Создать:** `packages/contracts/src/export/*`; `main/modules/reporting/application/export-json.ts`; тесты (schema + use case).

## 7. Модель предметной области

Измерения — в форме MeasurementDto (контракт TASK-028) — переиспользование, не новый формат; prefs — Prefs из TASK-047; шкалы — только код/версию (не данные — они в комплекте приложения).

## 8. База данных

Чтение через порты (measurement, settings, scale).

## 9. Бэкенд

Сборка последовательная (малые объёмы); counts вычисляются из фактов (не заявляются) — тест: counts === длинам массивов.

## 13. Бизнес-логика

formatVersion=1 — не меняется в MVP; правило эволюции (комментарий): новые поля — опциональные; ломающие — formatVersion 2 + читатель обеих версий (при появлении импорта). prefs может отсутствовать (не настроены) → undefined/null.

## 14. Безопасность

PHI в слепке — ожидаема (выгрузка пользователя); никаких секретов (ключей/токенов — их в БД и нет, тест-сверка списка корневых ключей).

## 15. Производительность

50k → ~10 МБ JSON, <3 с (ориентир на 5k ≤300 мс тест).

## 19. Стратегия тестирования

Schema: валидный минимальный слепок проходит; каждое ломающее поле (формат даты, отсутствие formatVersion) — отвергается; use case-интеграция: tmp-БД 3 записи + prefs + шкала → слепок → zod.parse ok → deep-сверка counts и полей первой записи; юникод/эмодзи roundtrip.

## 20. Критерии приёмки

- [ ] Слепок из реальной tmp-БД проходит `SnapshotSchema.parse` (roundtrip-тест).
- [ ] counts = фактическим длинам массивов (тест).
- [ ] Граничные поля (null-пульс, irregular=true, эмодзи в заметке) без искажений.
- [ ] formatVersion=1 в корне; appVersion присутствует.
- [ ] Ломающие кейсы схемы отвергаются (3 теста).
