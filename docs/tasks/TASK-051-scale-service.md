## 2. Цель

Миграция v4: таблица `reference_scale` (арх. 04 §3) + `app_event` (локальный журнал аналитики арх. 09 §9 — консолидировано в одну миграцию, чтобы не плодить технические версии); `ScaleService`: активация данных пакета TASK-050 при первом старте, идемпотентно, кэш в памяти; канал `scales/active`.

## 3. Бизнес-контекст

Единственная активная шкала на код с версией и источником (FR-4.5): UI и классификатор показывают «ESC/ESH 2018» рядом с каждой категорией — доверие через прозрачность. Обновление шкалы в будущем = новая запись версии + переключение, с показом пользователю, что изменилось.

## 4. Технический контекст

- **Архитектура:** reference_scale — арх. 04 §3; канал `scales/active` — 05 §3.
- **Модуль:** `analytics` (ScaleService — часть контекста аналитики) + `shared/db/migrations/v4`.
- **Обоснование (консолидация app_event):** таблица локальной аналитики (арх. 09 §9) не имеет собственного потребителя до P6; создание вместе с опорными данными P3 избегает выделенной «миграции ради таблицы». Отложенное обещание TASK-029 (app_event-события с P3) уточняется: таблица готова с этой задачи, записи `measurement_added` начнутся в P6 (TASK-103) — зафиксировано в TD-реестре PM-дока.
- **Нумерация (лиджер):** v2 FTS (045), v3 app_setting (047), **v4 reference_scale+app_event (051)**, v5 ai_summary (087), v6 chat_message (089), v7 network_event (075).

## 5. Объём

- **Включено:** миграция v4: `reference_scale (id TEXT PK, code TEXT NOT NULL, version TEXT NOT NULL, source_label TEXT NOT NULL, data_json TEXT NOT NULL, activated_at_utc INTEGER NULL, UNIQUE(code, version))`; `app_event (id TEXT PK, kind TEXT NOT NULL, payload_json TEXT NOT NULL, at_utc INTEGER NOT NULL)` + индекс (kind, at_utc); `ScaleService`: при старте — если активной шкалы bp_office_esc2018 нет → записать данные пакета TASK-050 (data_json), активировать (activated_at_utc); если есть — не трогать; при смене версии данных пакета (сравнение version) → записать новую версию, переключить активность, событие `scales:changed`? (не в MVP — комментарий); кэш в памяти; порт `ScaleRepository` + SQLite-адаптер; канал `scales/active {} → {code, version, sourceLabel, categories, homeBPNote, specialGroupsNote}` (контракт в TASK-054? НЕТ — сюда, канал маленький и нужен графику раньше; contracts-файл здесь); тесты.
- **Не включено:** UI-показ «что изменилось» при смене версии (пост-MVP), выбор стандарта пользователем (OQ-6 пост-MVP), запись app_event (потребители — P6 TASK-103).
- **Будущая работа:** несколько шкал активных (по типу показателя) — уже поддержано структурой code.

## 7. Модель предметной области

`ActiveScale = {code, version, sourceLabel, categories: ScaleCategory[], homeBPNote, specialGroupsNote}` — форма канала; сервис валидирует data_json zod-схемой пакета при чтении (повреждение → STORAGE/CORRUPT-стиль ошибка + лог, не тихий дефолт — шкала критична).

## 8. База данных

DDL v4 (§5). UNIQUE(code,version) — защита от дублей при повторной активации.

## 9. Бэкенд

## 19. Стратегия тестирования

Интеграционные (tmp-БД): миграция v4 создаёт таблицы; первый старт сервиса — активация (строка в БД); повторный — no-op (нет дубля — UNIQUE тест); смена версии данных (мок пакета с version 1.1.0) → новая версия активна, старая в истории; хендлер возвращает полную форму; app_event: вставка/чтение smoke (потребитель появится в P6).

## 20. Критерии приёмки

- [ ] Первый старт: шкала активна; повторный — дублей нет (UNIQUE-тест).
- [ ] Смена версии данных пакета → переключение активности с сохранением истории (тест).
- [ ] `scales/active` из рендерера возвращает категории и обе заметки (golden — сверка с пакетом).
- [ ] Повреждённый data_json → понятная ошибка + лог (тест).
