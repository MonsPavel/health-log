## 2. Цель

Второй канал обновлений `beta`: electron-updater channel-механика (beta.yml), переключатель в настройках, порядок публикации (beta → проверка → stable), изоляция (stable не видит beta).

## 3. Бизнес-контекст

Постепенное включение фич и ранний прогон релизов добровольцами — заменяет удалённые флаги (арх. 09 §4) и снижает риск stable-релиза.

## 4. Технический контекст

- **Архитектура:** каналы — арх. 10 §2.
- **Обоснование:** штатная механика electron-updater: `channel: 'beta'` → читает beta.yml; allowPrerelease; публикация rc-тегов в beta-канал того же релиза. Изоляция: stable-клиенты читают latest.yml (beta туда не попадает до перевода).

## 5. Объём

- **Включено:** electron-builder: вторая публикация beta.yml при пре-релизных тегах (`vX.Y.Z-beta.N`/`-rc.N` → beta-канал); `UpdatesService`: канал из prefs (`updateChannel: 'stable'|'beta'`), allowPrerelease = beta; `UpdatesSection` (TASK-097): select активируется, переключение → next-check применяет канал (подтверждение «перезапуск проверки»); процесс публикации в CONTRIBUTING/114: rc-тег → draft beta → прогон β-группой → promote в stable (пере-подпись не нужна — тот же артефакт, меняется фид); тесты с локальным фидом (104-хелпер): beta-клиент видит beta-версию, stable — нет.
- **Не включено:** отдельные сборки каналов (один артефакт, разные фиды — решение); автоматический promote.
- **Будущая работа:** alpha-канал при необходимости; опрос β-пользователей (вне продукта).
