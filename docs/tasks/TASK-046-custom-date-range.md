## 2. Цель

В панели фильтров — вариант «Произвольный»: два поля дат (от/до), состояние в URL (`period=custom&from=YYYY-MM-DD&to=YYYY-MM-DD`), валидация диапазона (from ≤ to, to не в будущем).

## 3. Бизнес-контекст

Врач спрашивает «покажите с 1 по 15 марта»; отчёт (TASK-068) будет использовать тот же механизм выбора периода — компонент строится один раз.

## 4. Технический контекст

- **Архитектура:** расширение state-machine фильтров TASK-044 (period='custom').
- **Обоснование:** нативные `input type="date"` (TD-11): доступность из коробки, ноль зависимостей, клавиатура; кастомный календарь-поповер — post-MVP при запросе UX.

## 5. Объём

- **Включено:** выбор «Произвольный» → появляются два date-input (от/до) с валидацией: from ≤ to (иначе — подсветка+текст), to ≤ сегодня (будущее — ошибка, EC-20-согласованность); URL-параметры from/to (ISO date строки, парсер с валидацией); конвертация дат в utcMs-границы: from = начало дня по настенной зоне, to = конец дня (23:59:59.999 настенного дня — включительно); применение к запросу; тесты конвертера (полночь/DST-границы) и UI.
- **Не включено:** календарь-виджет, пресет «этот месяц» (добавится тривиально, отложено).
- **Будущая работа:** сравнение двух периодов (пост-MVP аналитика).

## 6. Файлы

- **Создать:** `model/range.ts` (конвертация+валидация) + тесты; `ui/CustomRangeFields.tsx`.
- **Изменить:** `filters.ts` (state custom), `HistoryFilters.tsx`, i18n-ключи.

## 7. Модель предметной области

`parseRange(fromStr?, toStr?): {fromUtcMs, toUtcMs} | RangeError` — настенные даты (устройство) → границы utc через локальную зону; инвариант: записи включаются по настенному дню измерения (Instant.wallTime), не по utc-дню — согласовано с группировкой TASK-033.

## 12. Управление состоянием

## 13. Бизнес-логика

Границы: to-день включительно (до 23:59:59.999 настенного); ночная запись 00:15 «вчерашнего» дня по настенному — попадает во «вчера» (тест с tzOffset). DST-переход внутри диапазона: настенные дни не «дублируются» (тест с mock-зоной или фиксированным offset).

## 14. Безопасность

Мусорные URL-даты → валидатор → дефолт.

## 19. Стратегия тестирования

Юнит parseRange: нормальный диапазон, from>to, to в будущем, одно поле, мусор; ночные записи (tzOffsetMin −60) попадают в свой настенный день; компонент: URL→поля, ввод дат→URL, invalid-состояние блокирует применение (кнопка/авто).

## 20. Критерии приёмки

- [ ] from=1-го, to=15-го: записи обоих дней включительно в результате (включая 00:15 первого и 23:59 пятнадцатого настенного).
- [ ] from > to → ошибка валидации, запрос не уходит.
- [ ] to в будущем → ошибка (согласовано с EC-20).
- [ ] Мусор в URL `from=xx` → дефолт.
- [ ] Перезагрузка с custom-URL — диапазон восстановлен и применён.
