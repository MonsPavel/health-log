## 2. Цель

`container.ts` — единственное место сборки графа зависимостей: Clock → KeyVault → openEncrypted → MigrationRunner → репозитории → EventBus → регистрация хендлеров IPC. Приложение стартует с реальной зашифрованной БД в userData.

## 3. Бизнес-контекст

Ручной DI (D13) — простота и полный обзор графа в одном файле; без него зависимости размазываются по импортам и тесты теряют подстановку портов. Пользовательский результат: данные лежат зашифрованными, приложение их открывает при каждом старте.

## 4. Технический контекст

- **Архитектура:** composition root — арх. 03 §5 (ручной DI, без фреймворка).
- **Модули:** security (vault), shared/db (открытие+миграции), measurement (репозиторий), events (шина), ipc (регистрация).
- **Обоснование:** без DI-фреймворка: граф мал; пересмотр при >10 модулей (арх. 03 §5).

## 5. Объём

- **Включено:** `buildContainer(deps): Container` с параметрами для тестов (`{userDataPath, clock, vault?}` — переопределяемо); порядок инициализации: paths → logger (TASK-010) → vault.ensureKey → openEncrypted(dbPath, keyHex) → миграции → репозиторий → события; регистрация существующих IPC-хендлеров (ping — TASK-008); экспорт `Container` типа; bootstrap вызывает buildContainer с реальными зависимостями; лог «container ready» с фактами (версия схемы, created ключ).
- **Не включено:** прикладные use case'ы (029+ — регистрируются здесь же по мере появления: место помечено), SettingsStore (TASK-047).
- **Будущая работа:** graceful shutdown: закрытие БД на `will-quit` (включить сюда же — дёшево и важно для WAL-чекпоинта; включено в объём).

## 6. Файлы

- **Создать:** `apps/desktop/src/main/container.ts`; тест (buildContainer на tmp-userData с FixedClock и mock-vault → миграции применены, ping работает).
- **Изменить:** `apps/desktop/src/main/app/bootstrap.ts` (вызов контейнера; will-quit → db.close()).

## 7. Модель предметной области

`Container { db: Database; clock: Clock; vault: KeyVault; measurementRepo: BpMeasurementRepository; events: EventBus; logger: Logger }` — поля добавляются по мере задач. Порядок полей = порядок инициализации (конвенция читаемости).

## 8. База данных

Путь БД: `<userData>/health-log.db` (+ `-wal`, `-shm`). Закрытие: `db.pragma('wal_checkpoint(TRUNCATE)')` затем `close()` на выходе — чистое отсутствие -wal/-shm после выхода (NFR-2-гигиена).

## 9. Бэкенд

Init-ошибки пробрасываются выше bootstrap → глобальный хендлер TASK-011 (диалог + код): VAULT/KEY_MISSING при существующей БД — уже осмысленный сценарий пользователя (восстановление — TASK-101).

## 13. Бизнес-логика

Тест-параметры: контейнер не читает сам app.getPath (принимает пути параметрами) — тестируемость; bootstrap подставляет реальные пути. Отказ vault/БД → контейнер не создаётся (throw) — приложение не в «полуживом» состоянии.

## 14. Безопасность

keyHex живёт только в контейнере (поле не экспортируется наружу renderer); путь БД — внутри userData; всё остальное — свойства нижележащих задач.

## 15. Производительность

Инициализация: decrypt ключа + миграции + подготовка statements — <100 мс (замер в тесте-ориентире).

## 18. Телеметрия

## 19. Стратегия тестирования

Интеграционный: tmp-userData → buildContainer с FixedClock и мок-vault (без safeStorage — фабрика vault переопределяема) → ping-вызов через зарегистрированный каркас → файл БД существует, schema_version=1; повторный buildContainer на том же userData → миграций нет, данные сохранены; will-quit-симуляция → close → -wal отсутствует.
