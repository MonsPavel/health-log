## 2. Цель

Runner forward-only миграций по `meta.schema_version`: каждая миграция — транзакционный DDL; перед применением вызывается hook снапшота (интерфейс сейчас, реализация — TASK-070); сбой миграции не оставляет полусозданной схемы.

## 3. Бизнес-контекст

Схема будет меняться весь жизненный цикл (v1 здесь → v6 к P5). Стратегия отката (арх. 04 §5): даун-миграций нет, откат = восстановление автокопии. Значит runner + hook автокопии — фундамент безопасности всех будущих изменений схемы. Позиция: до первой миграции v1 (TASK-025).

## 4. Технический контекст

- **Архитектура:** миграции — `docs/architecture/04-database.md` §5; отказы — EC-14.
- **Модуль:** `shared/db` (не модуль measurement — миграции общесистемные).
- **Обоснование:** свой runner (~80 строк) вместо интегрированных миграций Drizzle: нужен hook автокопии и транзакционность DDL в SQLite (DDL транзакционен в SQLite — ключевое преимущество); контроль важнее удобства. Альтернатива Drizzle-migrate: известный формат, но hook придётся обходить — принято своё.

## 5. Объём

- **Включено:** `MigrationRunner`: реестр миграций `[ {version: 1, up: (db) => void}, … ]` (пополается задачами); чтение `meta.schema_version` (таблица meta создаётся runner'ом при первом запуске); применение всех миграций с version > текущей; каждая в транзакции (`BEGIN…COMMIT`, DDL внутрь); обновление schema_version в той же транзакции; hook `beforeMigration(version): Promise<void>` (интерфейс + no-op реализация по умолчанию, заменяется TASK-070); лог каждой миграции; ошибки: сбой → rollback → проброс `STORAGE/MIGRATION_FAILED` с номером версии; тесты: последовательность v1→v2 на tmp, сбой посреди миграции (тестовая миграция с ошибкой в середине DDL) → схема осталась на предыдущей версии, hook вызван до DDL.
- **Не включено:** реализация снапшота (TASK-070: VACUUM INTO+шифрование), миграции как таковые (025+), down-миграции (TD-2).
- **Будущая работа:** проверка «БД новее приложения» (schema_version > известного) → явная ошибка «обновите приложение» — включить сразу (дёшево, EC-25 семантика).

## 13. Бизнес-логика

Транзакционность: в SQLite DDL внутри транзакции откатывается — тест обязателен (не все СУБД так умеют). Идемпотентность: повторный запуск при актуальной версии — no-op (hook не вызывается). Hook вызывается один раз перед каждой применяемой миграцией (не перед каждой проверкой).

## 14. Безопасность

Миграции выполняются над зашифрованной БД (открытой с ключом) — hook снапшота обязан сохранять шифрование (требование к TASK-070, комментарий в интерфейсе hook'а).

## 15. Производительность

Проверка версии — один SELECT; ожидаемое время старта миграций — миллисекунды; автокопия (потом) — секунды на больших БД, не блокирует UX (прогресс — забота TASK-070).

## 18. Телеметрия

Лог: `migrating v{N-1}→v{N}`, `migrated to v{N}` (категория db).

## 19. Стратегия тестирования

Интеграционные тесты на tmp: (1) свежая БД → 2 тестовые миграции → schema_version=2, объекты созданы; (2) повторный запуск — no-op; (3) миграция с намеренным сбоем посреди → rollback: предыдущие объекты целы, версия не изменилась, hook-спай вызван до DDL (порядок!); (4) файл БД с schema_version больше известной → DB_NEWER_THAN_APP.

## 20. Критерии приёмки

- [ ] Тесты (1)–(4) §19 зелёные.
- [ ] Сбойная миграция не оставила ни одного объекта (таблица тестовой миграции отсутствует после rollback).
- [ ] Hook вызывается ровно перед каждой применяемой миграцией и ни при no-op.
- [ ] Коды STORAGE/MIGRATION_FAILED (с params {version}) и STORAGE/DB_NEWER_THAN_APP экспортированы.
