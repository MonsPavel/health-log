## 2. Цель

`RestoreBackup({file, passphrase})`: валидация контейнера (magic/манифест/sha256/GCM) → план восстановления с предупреждениями (замена текущих данных; «копия старее»; «копия от другой схемы» — отказ с понятным текстом) → подтверждение → замена БД → перезапуск состояния приложения.

## 3. Бизнес-контекст

UC-08 (новый ПК/после краха): восстановление — операция повышенного риска (заменяет живые данные). Каждый отказ — до касания текущих данных (AC-2.5); успех — полная замена, включая схемы и FTS.

## 4. Технический контекст

- **Архитектура:** Data Care инвариант — арх. 02 §3.5 («без проверки целостности — нет восстановления»); EC-25.
- **Обоснование:** восстановление = подмена файла БД + перезапуск приложения (не in-place merge): самый простой и надёжный путь; сервисный перезапуск (`app.relaunch()+exit(0)`) — штатно.

## 5. Объём

- **Включено:** `RestorePlan`-фаза: parse контейнера → magic? манифест zod? GCM-расшифровка passphrase → sha256(db) == манифест → план: `{schemaVersion копии vs текущая: equal|older|newer, createdAtUtc, counts, currentCounts}`; решения: newer schema → отказ `BACKUP/DB_NEWER` («обновите приложение»); passphrase неверна → `BACKUP/WRONG_PASSPHRASE`; подтверждение (renderer) → execute: закрыть БД → бэкап-текущей в tmp (страховка отката!) → подменить файл БД расшифрованным снапшотом → relaunch; миграции применятся при старте если older (своим runner'ом); канал `backup/restore {file, passphrase, confirmed}` двухфазный: `plan` → `execute`; тесты.
- **Не включено:** merge-восстановление (смешивание с текущими данными — никогда: замена, решение SRS UC-08), выборочное восстановление.
- **Будущая работа:** восстановление из копии при повреждённой текущей БД (TASK-101 переиспользует execute с пропуском plan-сравнения текущей).

## 6. Файлы

- **Создать:** `main/modules/data-care/application/restore-backup.ts` (+plan/execute) + интеграционные тесты; contracts `backup/restore` (двухфазный).

## 7. Модель предметной области

`RestorePlan {manifest, schemaDelta: 'equal'|'older'|'newer', warnings: ['replaces-current', 'older-than-current'?]}`; execute — только после явного confirmed=true из renderer (второй вызов) — против случайного двойного клика.

## 8. База данных

Подмена: БД закрыта (checkpoint), файлы db/-wal/-shm удалены, расшифрованный снапшот на место db; страховка: текущая БД → tmp (если расшифровка/открытие копии упало после подмены — вернуть назад, тест).

## 9. Бэкенд

Relaunch после успешной подмены: контейнер закрыт, `app.relaunch(); app.exit(0)`; клиенту рендерера ответ до relaunch (канал завершится —-relaunch через 500 мс отложенно, чтобы ответ ушёл — деталь реализации, зафиксировать).

## 10. Фронтенд

N/A (073); контракт: план → UI показывает предупреждения → пользователь подтверждает → execute.

## 11. API

`backup/restore`: фаза 1 `{file, passphrase} → {plan}|ошибки`; фаза 2 `{…, confirmed: true} → {restarting: true}`.

## 12. Управление состоянием

После relaunch приложение стартует на восстановленных данных (кэши пусты — чисто).

## 13. Бизнес-логика

Older schema: копия v1 на приложении с v3 → restore → миграции при старте поднимут до v3 (данные совместимы вперёд); newer → отказ. counts-предупреждение: «в копии 120 записей, сейчас 350 — текущие будут заменены» (факт, не оценка). Текущая пустая БД → предупреждение replaces-current всё равно показывается (согласованность).

## 14. Безопасность

Passphrase не логируется (redact); попытки перебора — rate-limit НЕ нужен (локальный файл, пользователь сам); временная страховка-копия удаляется после успешного relaunch (или остаётся до следующей — решение: остаётся в tmp, ОС чистит; безопасно — зашифрована? tmp-копия НЕ зашифрована! → решение: страховка хранится шифрованной (быстрый createBackup auto с тем же passphrase копии) или удаляется немедленно после успешного старта; ПРИНЯТО: страховка — auto-копия с тем же passphrase (шифрована), путь tmp, удаление при успешном старте по флаг-файлу).

## 15. Производительность

Расшифровка 20 МБ ~0.5 с; подмена мгновенна; relaunch ~2 с — UX честен («приложение перезапустится»).

## 16–17. Доступность / i18n

## 18. Телеметрия

Лог: `restore plan schemaDelta=older counts=…; execute…; success` (без путей/пароля).

## 19. Стратегия тестирования

Интеграционные (tmp): happy (равная схема): подмена + relaunch-флаг; старее → план older; новее → отказ DB_NEWER до execute; неверный passphrase → WRONG_PASSPHRASE (дважды — не деградирует); битый sha256 → отказ; откат-страховка: подмена с битым снапшотом-в-контейнере? (недостижимо после sha256 — вместо: сбой расшифровки после закрытия БД → текущая возвращена, тест).

## 20. Критерии приёмки

- [ ] Happy: после execute приложение перезапустилось на данных копии (счётчик записей равен манифесту).
- [ ] Newer schema → отказ ДО закрытия текущей БД (текущие данные работают).
- [ ] Неверный пароль → WRONG_PASSPHRASE, БД не тронута.
- [ ] Битый sha256 → отказ целостности.
- [ ] Страховка: сбой после закрытия → текущая БД возвращена (тест-кейс), данные работоспособны.
- [ ] Execute без plan-фазы (confirmed без валидного файла) → отказ.
