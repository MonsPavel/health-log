## 2. Цель

Flat-config ESLint с правилами качества TypeScript и **зонными правилами границ** (renderer без Node, domain без внешних импортов, `main/modules/<m>` не импортирует внутренности соседних модулей); Prettier как единственный форматтер; корневой скрипт `lint`.

## 3. Бизнес-контекст

Монолит без механически проверяемых границ превращается в «большой шар» — главный риск сопровождаемости (арх. 01 §4). Бизнес-следствие: скорость безопасного добавления фич (включая будущих агентов-кодировщиков) прямо зависит от того, что нарушение архитектуры = красная сборка, а не код-ревью глазами.

## 4. Технический контекст

- **Архитектура:** матрица зависимостей `docs/architecture/03-modules.md` §4; boundary-правила дублируются dependency-cruiser (TASK-005) — две сети защиты.
- **Пакеты:** корень + все пакеты.
- **Обоснование:** eslint-plugin-boundaries для зон + `no-restricted-imports`/`import/no-nodejs-modules` для renderer. Альтернатива — только dependency-cruiser: он проверяет граф пакетов, но хуже работает с файловыми зонами внутри `apps/desktop`; компромисс: два инструмента с пересекающимися правилами (согласованы в §13).

## 5. Объём

- **Включено:** `eslint.config.js` (flat): TS-парсер, recommended-type-checked, правила `no-restricted-syntax` на `any`/`ts-expect-error` без описания, зонные правила, отдельный оверрайд для `*.test.ts` и `tools/`; `.prettierrc` (printWidth 100, singleQuote, trailingComma all); скрипт `lint`/`lint:fix`; автозапуск prettier через `prettier --check` в `lint`.
- **Не включено:** dependency-cruiser (TASK-005), запрет сети (правило появится в TASK-075 в тот же конфиг), husky/lint-staged (решено: без git-хуков — соло-разработка + CI-гейт TASK-014; долг TD-IMP-2).
- **Будущая работа:** i18n-плагин при первых ложных срабатываниях скрипта ключей (TASK-013).

## 6. Файлы

- **Создать:** `eslint.config.js`, `.prettierrc`, `.prettierignore`.
- **Изменить:** корневой `package.json` (скрипты), `packages/*/package.json` (нет — скрипты делегируются корнем).

## 13. Бизнес-логика

Правило качества: нарушение зоны = **error** (не warning); `--max-warnings 0` в скрипте. Согласованность с dependency-cruiser: матрица в §7 — единственный источник, оба инструмента читают одну семантику (документ-комментарий в `eslint.config.js` ссылается на арх. 03 §4).

## 14. Безопасность

Зона renderer без Node — часть модели угроз (арх. 08 §4). Дополнительно: правило, запрещающее `eval`/`new Function` во всех зонах.

## 15. Производительность

Lint полного репо на P0 ≤10 с; typed-linting требует projectService — включить `projectService: true` (быстрее parserOptions.project на больших деревьях).

## 19. Стратегия тестирования

Тест правил: фикстуры `tools/lint-fixtures/{violation-renderer-node.ts,violation-domain-npm.ts,ok-cross-module-index.ts}`; скрипт запускает ESLint API на фикстурах и ожидает: два нарушения — error, корректный — чисто. Фикстуры исключены из основного линта (ignore), проверяются скриптом.

## 20. Критерии приёмки

- [ ] `pnpm lint` зелёный на чистом репо (включая prettier --check).
- [ ] Фикстура «renderer импортирует node:fs» даёт error; «domain импортирует lodash» — error; «модуль A импортирует модуль B через index.ts» — чисто.
- [ ] `any` и голый `@ts-expect-error` (без пояснения в той же строке) — error.
- [ ] `pnpm lint` ≤15 с на P0-объёме.

## 24. Проверка

Автоматически: `pnpm lint` exit 0; `pnpm run test:lint-rules` (скрипт фикстур) — «2 violations expected, ok-fixture clean». Ручная: временно добавить `import fs from 'node:fs'` в `src-renderer` → `pnpm lint` красный; убрать → зелёный. Откат: revert; зависимости ни на чём не лежат кроме TASK-002 (строгие типы независимы).
