## 2. Цель

Ни одна ошибка — ни в main, ни в renderer — не остаётся невидимой и не показывает пользователю технический мусор: main перехватывает uncaughtException/unhandledRejection; renderer имеет ErrorBoundary-каркас и тосты; клиентские ошибки доставляются в общий лог.

## 3. Бизнес-контекст

NFR-12: понятные сообщения с следующим шагом, стеки — только в локальных логах. Для доверия к «дневнику здоровья» крах экрана = потеря доверия к данным; гасить ошибки надо единообразно с первого экрана. Позиция: каркас до фич — иначе каждая фича добавит свой ad-hoc обработчик.

## 4. Технический контекст

- **Архитектура:** сквозная обработка ошибок — `docs/architecture/09-platform.md` §10; таксономия кодов там же.
- **Пакеты:** `@hl/contracts` (канал `app/log-client-error`), `apps/desktop` (main + renderer).
- **Обоснование:** ошибки как значения (Result, TASK-006) покрывают ожидаемые отказы; глобальные хендлеры — страховка от неожиданных. Оба механизма обязательны (разные классы сбоев).

## 5. Объём

- **Включено:** main: хендлеры `process.on('uncaughtException'|'unhandledRejection')` → лог (категория app, уровень error, cause) → безопасный диалог `dialog.showMessageBox` c локализуемо-нейтральным текстом-константой и кодом ошибки; guard от циклов диалогов (не более 1 активного, счётчик подряд >5 → тихий лог); renderer: `AppErrorBoundary` (class-компонент, props: fallback-функция, onError) — логирует в main через канал `app/log-client-error {code:'APP/RENDERER', messageKey, digest}` + показывает fallback; корневой boundary в `App` + системный тост `showToast(error)` — минимальный компонент (текст по messageKey через i18n, кнопка «Закрыть»); хелпер `toUserMessage(AppErrorDto)` → строка по каталогу с fallback на `errors.internal`.
- **Не включено:** экраны кризисных состояний (повреждение БД — TASK-101), sentinel-мониторинг (вне MVP), ретраи (уровень каналов, TASK-075+).
- **Будущая работа:** дедупликация повторных крашей рендерера с автоперезагрузкой окна (если частота >3/мин — предложение «перезагрузить»).

## 6. Файлы

- **Создать:** `apps/desktop/src/main/app/global-errors.ts`; `src-renderer/app/{ErrorBoundary.tsx,toast.tsx,errors.ts}`; `src-renderer/i18n/ru/errors.json` (начальный: `internal`, `validation`, `renderer`); тесты.
- **Изменить:** `bootstrap.ts` (регистрация хендлеров), `App.tsx` (обёртка boundary), `packages/contracts` (канал `app/log-client-error`).

## 9. Бэкенд

Канал `app/log-client-error` — fire-and-forget (handler возвращает `{ok:true,data:null}`, ошибки логирования глушатся — логгер не должен ломать UI цепочкой). Диалог краша main: показывается максимум один; текст: «Произошла непредвиденная ошибка. Данные не затронуты. Код: {code}» (константа, RU — каталог рендерера не доступен main; фиксируется как допустимое исключение с комментарием).

## 10. Фронтенд

Boundary-иерархия: корневой (каркас, fallback — полноэкранный «Что-то сломалось, перезагрузите») + per-feature границы (появляются с фичами; конвенция в комментарии AppErrorBoundary). Toast: очередь max 3, авто-скрытие 6 с, role="status" (a11y).

## 11. API

`app/log-client-error`: request zod `{code: z.literal('APP/RENDERER'), messageKey: z.string().max(200), digest: z.string().max(64)}`, response `null`. Ошибки конверта на этом канале — глушатся (см. §9).

## 12. Управление состоянием

N/A (тост — локальный store-каркас без zustand, useState в провайдере).

## 13. Бизнес-логика

Классификация: ожидаемый отказ (Result/AppError) — обрабатывается на месте вызывающим; неожиданный (throw) — глобальные хендлеры. Правило пограничного случая: ошибка внутри обработчика ошибки → лог в stderr-файл напрямую (без рекурсии через pino). Восстановление после renderer-краша: пользователь перезагружает (Ctrl+R работает в dev; prod — кнопка fallback «Перезагрузить» → location.reload()).

## 14. Безопасность

Клиентский канал валидируется zod (недоверенный рендерер); digest ограничен 64 символами; диалог main не отображает message исключения (только code) — против утечки путей/данных через случайный текст.

## 15. Производительность

Ошибка ≠ деградация: boundary не ре-рендерит всё дерево (изолирован per-feature); логи ошибок — асинхронный append.

## 16. Доступность

Тост: `role="status"`, `aria-live="polite"`; фокус не уводится; полноэкранный fallback — `role="alert"`, кнопка в tab-порядке.

## 17. Интернационализация

Все пользовательские тексты ошибок — ключи `errors.*`; текст диалога main — RU-константа с комментарием-исключением (см. §9); fallback-сообщение boundary — ключ.

## 18. Телеметрия

Клиентские ошибки — в общий лог с полем `source: renderer`, digest для агрегации вручную; никаких внешних репортеров (FR-7.2).

## 19. Стратегия тестирования

Main: тест хендлеров с подменёнными process.on-регистрациями — вызов → лог-спай + диалог-спай (mock electron.dialog); guard-счётчик диалогов. Renderer: React Testing Library — компонент, бросающий исключение в потомке → fallback отрисован, канал `app/log-client-error` вызван (mock window.hl); тост: появление/автоскрытие/role.

## 20. Критерии приёмки

- [ ] Искусственный throw в main-хендлере (вне registerChannel — прямой вызов хендлера ошибки в тесте) → запись в логе app с cause, диалог-спай вызван 1 раз.
- [ ] 6 подряд ошибок → диалог показан 1 раз (guard), в логе 6 записей.
- [ ] Компонент-исключение внутри boundary → пользователь видит fallback, в main-логе появилась запись source=renderer.
- [ ] Тост по невалидному messageKey показывает `errors.internal` (fallback), не «undefined».
- [ ] Тесты a11y-атрибутов тоста/фолбэка зелёные.
