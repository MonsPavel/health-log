## 3. Бизнес-контекст

## 4. Технический контекст

- **Архитектура:** read-path — арх. 05 §5; read model — 03 §2 (measurement публикует ListByPeriod).
- **Модуль:** `measurement/application` + `main/ipc`.
- **Обоснование:** list — тонкий use case над listByPeriod (без доменных правил) — допустимо «прокладкой» use case'а для единообразия регистрации и будущего кэширования.

## 5. Объём

- **Включено:** `ListMeasurementsUseCase.execute(query)` → `{items: MeasurementDto[], total}`; дефолты: limit=200 (макс 500 — валидация схемы clamp), offset=0; регистрация `measurements/list`; юнит-тесты (fake repo) + интеграционный (SQLite tmp).
- **Не включено:** группировка по дням (renderer, TASK-033), FTS (045), update/delete use cases (037 — но хендлеры? решено: хендлеры тоже 037, здесь только list; ping-стиль прототип delete не пишется).
- **Будущая работа:** курсор.
