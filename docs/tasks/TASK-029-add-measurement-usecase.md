## 2. Цель

Прикладной сценарий `addMeasurement`: валидация домена → выборка недавней истории → эвристики опечатки/дубля → сохранение → ответ с флагами и criticalValue; публикация событий `measurement:changed`, `data:versionBumped`.

## 3. Бизнес-контекст

UC-01 с альтернативами A1–A3 (SRS 06): пользователь за ≤15 с сохраняет измерение; система бережно предупреждает об опечатке/дубле и — при критических значениях — сразу готовит сигнал для панели срочности (FR-7.4). Это первый сквозной поток «UI → домен → шифрованная БД → UI».

## 4. Технический контекст

- **Архитектура:** application-слой — арх. 02 §5; события — 01 §5; последовательность — 05 §5.
- **Модуль:** `measurement/application`; регистрация — `main/ipc`.
- **Обоснование:** use case оркестрирует и публикует события; адаптер — нет (TASK-026 §12); UI решает, что показать по флагам (TASK-032) — логика в main, UX в renderer.

## 5. Объём

- **Включено:** `AddMeasurementUseCase {execute(cmd): Promise<Result<AddResult>>}`: (1) `BpMeasurement.create` (домен, с Clock) → Result err наружу; (2) выборка истории: listByPeriod(14 дней до takenAt, лимит 100) для TypoHeuristic + recent 10 для DuplicateDetector; (3) флаги; (4) repo.add; (5) events.emit(measurement:changed, data:versionBumped); (6) лог; регистрация хендлера `measurements/add` в контейнере (TASK-027 точка расширения); юнит-тесты с fake-repo и FixedClock.
- **Не включено:** диалоги (TASK-032), FTS (TASK-045), хендлеры list (TASK-030).
- **Будущая работа:** флаг-«two-step save» для критических значений — не делается: сохранение всегда происходит (UC-06), панель после.

## 6. Файлы

- **Изменить:** `apps/desktop/src/main/container.ts` (инстанцирование + регистрация).

## 7. Модель предметной области

`AddResult = {measurement: MeasurementDto; flags: {typo?: TypoFlag; duplicate: boolean; criticalValue: CriticalFlag}}`. Зависимости конструктора: `{repo, clock, events, logger}` — подстановочные в тестах.

## 8. База данных

Через порт (TASK-026); здесь БД-логики нет.

## 9. Бэкенд

Порядок и отказы: домен-ошибка → Result err (валидация, FUTURE_TIME и т.д.) — БД не трогается; эвристики — после валидации, до сохранения; сохранение упало (STORAGE/*) → err + лог; события — только после успешного add. Хендлер: zod (TASK-008 каркас) → use case → Result→ApiResult маппинг.

## 10. Фронтенд

N/A (потребление — TASK-031/032).

## 11. API

`measurements/add` (TASK-028) — реализация. Ответ-флаги: typo (TypoFlagDto), duplicate (bool), criticalValue ('high'|'low'|undefined). События: `measurement:changed {profileId}`, `data:versionBumped {newVersion}` — при успехе всегда оба.

## 12. Управление состоянием

Инвалидация — на стороне renderer (TASK-033: подписка на `measurement:changed` → invalidateQueries(['measurements'])).

## 13. Бизнес-логика

Граничные: duplicate+typo одновременно — оба флага в ответе (UI покажет одну сборную подсказку — решение TASK-032); сохранение при флагах происходит только после подтверждения пользователя — это второй вызов add с флагом `forceConfirm: true`? РЕШЕНИЕ: нет второй стадии на уровне use case — UI сам решает повторно вызвать после подтверждения; use case всегда сохраняет и всегда возвращает флаги. Документируется: флаги информационные, не блокирующие. Конкурентность: два быстрых вызова — оба сохранятся (нет блокировок); дубль-детектор сработает на втором (окно 2 мин) — семантика приемлема.

## 14. Безопасность

profileId из запроса — используется как есть (валиден по схеме); будущий session-scope (арх. 08 §3) подменит источник на сессию — точка расширения комментарий.

## 15. Производительность

Полный путь add ≤50 мс (тест-ориентир: fake-repo; на SQLite — замер в интеграционном тесте TASK-026-стиля) — UX-цель «мгновенно».

## 18. Телеметрия

## 19. Стратегия тестирования

Юниты (fake repo, FixedClock, spy events): happy-path (события оба, флаги пустые); домен-ошибка (будущее время) → err, БД не тронута (spy), событий нет; typo-флаг (история из 14 дней 128/82, кандидат 169/82); duplicate-флаг; критический high → criticalValue='high'. Интеграционный: через контейнер tmp-БД → реальный вызов хендлера → запись в БД (mappers roundtrip).

## 20. Критерии приёмки

- [ ] Happy-path: Result ok, в fake-repo запись есть, оба события отправлены, флаги пустые.
- [ ] Будущее время: err FUTURE_TIME, add не вызван, событий нет.
- [ ] Typo-история: flags.typo={field:'sys',…}; duplicate: flags.duplicate=true; 200/130 → criticalValue='high'.
- [ ] Интеграционный тест через контейнер: запись реально в SQLite, read-back равен.
- [ ] Хендлер зарегистрирован; вызов из renderer (ручной ping-подобный) работает.
