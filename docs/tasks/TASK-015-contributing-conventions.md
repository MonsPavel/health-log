## 2. Цель

`CONTRIBUTING.md` в корне: как собрать проект с нуля, какие команды выполнять, как оформлять ветки/коммиты/PR, чек-лист готовности задачи, карта документации и правил (границы, i18n, PHI, безопасность).

## 3. Бизнес-контекст

Проект с одним мейнтейнером и агентами-кодировщиками нуждается в письменных конвенциях не меньше командного: риск R-8 (bus-factor) и риск «агент сделал не так» закрываются одним документом, на который ссылается каждый TASK-файл через DoD. Правила дорожной карты («задача готова = проверка зелёная») обязаны жить в репозитории, не только в docs.

## 4. Технический контекст

- **Архитектура:** N/A — документ; фиксирует ссылки на `docs/architecture/03-modules.md` §4 (границы), `docs/tasks/_TEMPLATE.md` §21 (DoD), `docs/roadmap/README.md` (правила изменения объёма).
- **Обоснование:** один файл вместо разрозненных — единственная точка входа; длинные регламенты не пишутся (принцип: документ читают, а не хранят).

## 5. Объём

- **Включено:** разделы: (1) Требования (node 20, pnpm 9, corepack enable); (2) Быстрый старт (clone → pnpm install → pnpm dev — все команды проекта с пояснением); (3) Ветвление: `feat/…`, `fix/…`, `docs/…`, `chore/…`; (4) Коммиты: Conventional Commits (`feat:`, `fix:`, `docs:`, `chore:`, `test:`, `refactor:`); (5) PR: название, ссылка на TASK-ID, чек-лист DoD из `_TEMPLATE.md` §21 скопирован; (6) Правила: границы импортов (ссылка 03 §4 + команды проверки), i18n (только ключи + `pnpm check:i18n`), PHI (красный список полей логов), сеть (только EgressGateway — с P5), тесты (что обязано иметь тесты: домен — всегда, use case — всегда, UI — критические пути); (7) Definition of Done задачи (шаблон §21); (8) Required checks main (из TASK-014) и правило admin-merge только для CI-починки.
- **Не включено:** архитектурные документы (ссылки, не копии), регламент релизов (появится в TASK-114).
- **Будущая работа:** англоязычная версия (пост-MVP, если open source — OQ-2).
