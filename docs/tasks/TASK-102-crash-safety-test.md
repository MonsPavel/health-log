## 2. Цель

Автоматизированный скрипт: приложение пишет поток вставок (батчами, через test-only канал) → убийство процесса kill -9 в случайный момент → перезапуск → инварианты: (1) все записи подтверждённых батчей целы, (2) схема цела, (3) data_version согласован (≥ записей), (4) N итераций без единого нарушения.

## 3. Бизнес-контекст

Главный страх пользователя R-4 и прямое требование NFR-3/DoD: «внезапное отключение питания не теряет сохранённое». Без этого теста «WAL и транзакции» — вера, а не гарантия.

## 4. Технический контекст

- **Архитектура:** NFR-3; паттерн test-hook — как TASK-062 (HL_BENCH → переименовать семейство: HL_TEST_HOOKS=1 — общий флаг для seed/bench/crash-каналов; TASK-062/077/081 используют HL_BENCH/HL_FAKE — УНИФИКАЦИЯ: оставить существующие имена, добавить общий `__test/*` префикс каналов; документировать).
- **Обоснование:** kill -9 (taskkill /F) — жёстче ОС-выключения (нет flush-шансов): гарантия «не хуже, чем питание». Инвариант «подтверждённое = целое»: тест-канал подтверждает батч ответом; всё, что ack'нуто до килла, обязано быть в БД после.

## 5. Объём

- **Включено:** test-канал `__test/insert-batch {count} → {committedTotal}`: вставка count записей ОДНОЙ транзакцией + data_version bump, возвращает подтверждённый total; `tools/scripts/crash-test.mjs`: цикл N=10 итераций: launchApp(tmp-userData) → калибровка (10 батчей ack'нуты) → цикл: посылать батчи по 50, отслеживать ack-и, случайно (детерминированный PRNG seed) kill -9 между ack'ами (окно 50–500 мс) → перезапуск → через канал `app/meta`+list: count ≥ последнего ack, schema_version актуальна, data_version ≥ count → зафиксировать итерацию; отчёт; скрипт `test:crash`; Windows-специфика: taskkill /F /PID.
- **Не включено:** CI-интеграцию (локально + тег — TASK-105), тесты дисковых сбоев (вне возможностей).
- **Будущая работа:** стохастика с реальным выключением питания (только лабораторно — вне проекта).

## 8. База данных

Проверяемые свойства: count ≥ ackTotal (никто не потерян), count ≤ ackTotal + 49 (незакрытый батч мог частично… НЕТ: транзакция батча атомарна → count либо ack, либо ack+0 (недо-batch отброшен) → строгий инвариант: count == ack ИЛИ ack < count < ack+50 невозможно… точный инвариант: count ∈ {ack} (транзакция завершилась до килла) — count == последнему ack ИЛИ == ack (батч в полёте откатился). Плюс: data_version == count + базовые (согласованность: каждая запись = +1) — проверка формулы dv == 1 + count.

## 9. Бэкенд

insert-batch: одна транзакция на батч (не по записи) — реалистичная нагрузка + быстрый тест; данные синтетические.
