## 2. Цель

Незаполненная/частично заполненная форма переживает перезапуск приложения: zustand-хранилище формы получает persist в localStorage (ключ `hl.formDraft`); черновик очищается после успешного сохранения и после явного сброса.

## 3. Бизнес-контекст

NFR-3: «черновик незаполненного ввода восстанавливается после краша». Пользователь (П1) замерил давление, начал вводить — приложение упало/ноутбук уснул с крахом: повторный ввод с нуля = трение, убивающее привычку.

## 4. Технический контекст

- **Архитектура:** арх. 06 §3 (zustand persist — эфемерное UI-состояние; истина в БД).
- **Пакет:** renderer feature `measurement`.
- **Обоснование:** localStorage (не БД): черновик — несессии-критичное UI-состояние; синхронный доступ до первого рендера; политика «никаких данных пользователя в localStorage» (TASK-013 §14) уточняется: черновик ввода — временное исключение с осознанным риском (данные уже на локальной машине; риск эквивалентен незакрытой форме) — документируется в комментарии store. Альтернатива (хранить черновик в БД через IPC) — асинхронность ломает момент восстановления.

## 5. Объём

- **Включено:** persist-мидлварь zustand для `form-store`: поля `sys, dia, pulse, irregular, arm, note, when` (включая режим «заднее число»); частичная (partialize) — исключая transient-поля (состояние отправки); восстановление: при маунте формы — поля из persist (сообщение-тост «Черновик восстановлен» при непустом); очистка: onSuccess add/update (полная), явная кнопка «Очистить» в форме, cancelEdit (режим edit — черновик редактирования не персистится, только add-черновик); версия схемы persist (`version: 1, migrate`).
- **Не включено:** черновики в режиме правки (решение: edit всегда начинается заново из DTO — черновик правки не сохраняется), синхронизация между окнами.
- **Будущая работа:** TTL черновика (автоочистка >7 дней) — при запросах.

## 12. Управление состоянием

Zustand `persist({name: 'hl.formDraft', version: 1, partialize, migrate})`; восстановление синхронное при создании store (localStorage — синхронен); SSR-безопасность не нужна (нет SSR).

## 13. Бизнес-логика

Пограничные: (1) краш ПОСЛЕ успешного сохранения, но до очистки → восстановлен черновик, но запись уже есть → дубликат при повторном сохранении? Mitig: очистка store выполняется в onSuccess ДО тоста (порядок кода) и событие versionBumped переоткрывает список — остаточный риск минимален, принимается (честный комментарий); (2) системные часы ушли назад — when-режим «заднее число» сохраняет введённую строку, домен отклонит будущее (FUTURE_TIME) — согласованно; (3) повреждённый JSON в localStorage → persist migrate-фолбэк на дефолты (try/catch — тест).

## 14. Безопасность

Черновик в localStorage — локальные данные на машине пользователя (эквивалент открытой формы); попадание в экспорт/копии — НЕТ (localStorage не входит в резервные копии — задокументировать в TASK-070 манифесте как известное ограничение… нет: черновик не должен попадать в копии — так и есть, копируем только БД; комментарий в 070 при генерации).

## 15. Производительность

Запись в localStorage на каждое изменение поля — дёшево (debounce 200 мс, если профилировка покажет — сейчас без).

## 19. Стратегия тестирования

Тесты store: persist roundtrip (заполнить → пересоздать store с тем же localStorage → поля равны); partialize: submit-флаг не восстановлен; migrate v0→v1; повреждённый JSON → дефолты; очистка onSuccess. Компонентный: маунт формы с заполненным draft → поля предзаполнены + тост; кнопка «Очистить» → пусто и в localStorage.

## 20. Критерии приёмки

- [ ] Заполнить 3 поля → перезапустить приложение → поля восстановлены, тост «Черновик восстановлен».
- [ ] Успешное сохранение → localStorage `hl.formDraft` пуст (числовые поля), рука/флаги — по правилам TASK-031 (персистятся отдельно? РЕШЕНИЕ: arm/irregular — настройки предпочтений, НЕ черновик: переносятся в отдельный persist-ключ `hl.formPrefs`, который не очищается при сохранении).
- [ ] Кнопка «Очистить» — все черновиковые поля пусты.
- [ ] Повреждённый localStorage → дефолты без креша.
- [ ] Режим edit не пишет черновик.
