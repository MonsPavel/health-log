## 2. Цель

Полнотекстовый поиск по заметкам: миграция v2 (FTS5 virtual table + триггеры синхронизации), канал `notes/search`, строка поиска в истории; вставка/правка/удаление заметок автоматически синхронизируют индекс.

## 3. Бизнес-контекст

US-9: найти измерения по заметке («после кофе», «болела голова») — то, ради чего заметки пишутся. Для П2 это критерий выбора продукта против таблицы.

## 4. Технический контекст

- **Архитектура:** миграции — арх. 04 §5; канал — 05 §3 (`notes/search`).
- **Модуль:** `shared/db/migrations` (v2), `measurement/adapters` (search), contracts.
- **Обоснование:** FTS5 с content='bp_measurement' (external content) — индекс без дублирования текста; триггеры AFTER INSERT/UPDATE/DELETE. Ограничение: FTS5 без русской морфологии (нет стемминга ru) → стратегия поиска: точные подстроки-токены; принято как TD-IMP-3 (пересмотр при спросе на словоформы). Альтернатива LIKE %…% по всем записям: проще, но без индекса и ранжирования; на 50k записей LIKE приемлем (~десятки мс), но FTS5 готов к росту и даёт сниппеты.

## 5. Объём

- **Включено:** миграция v2: `CREATE VIRTUAL TABLE bp_measurement_fts USING fts5(note, content='bp_measurement', content_rowid='rowid')` + 3 триггера (insert/update/delete) на внешнее содержимое; backfill существующих заметок (INSERT INTO fts(rowid, note) SELECT rowid, note…); `SearchNotesUseCase`: запрос FTS5 MATCH с санитизацией запроса (пользовательский текст → безопасный MATCH-запрос: токены в двойные кавычки, спецсимволы нейтрализуются, пустой/мусорный → пустой результат, не ошибка); fallback: если MATCH дал 0 → LIKE-подстрока (решение: даёт подстрочный поиск поверх морфологического ограничения, документируется); канал `notes/search {query, limit=50} → {items: MeasurementDto[]}` (дедуп по записи); UI: строка поиска в панели фильтров (TASK-044-стиль, URL `?q=`), результат — тот же список (объединение с фильтрами: поиск сужает); тесты: индексация CRUD, поиск токен/подстрока/мусор.
- **Не включено:** морфология/стемминг (TD-IMP-3), ранжирование релевантности (сортировка по времени, не rank — решение), поиск по пульсу/числам.
- **Будущая работа:** unicode61 tokenizer с `tokenchars` для дефисов; ранжирование rank.

## 6. Файлы

- **Создать:** `shared/db/migrations/v2-fts.ts`; `measurement/adapters/notes-search.ts`; `application/search-notes.ts`; contracts `notes/search`; `ipc/handlers/search.ts`; UI-интеграция в `HistoryFilters`+`useMeasurements`; тесты (миграция, юзкейс, хендлер, UI).

## 7. Модель предметной области

`SearchResult = {items: MeasurementDto[]; query: string}`; запрос ≤100 символов (zod max) — анти-DoS от себя.

## 8. База данных

FTS5 external-content таблица + триггеры (§5); backfill идемпотентен (rebuild-команда `INSERT INTO fts(bp_measurement_fts) VALUES('rebuild')` — используется и как repair). Тест: после update заметки поиск находит НОВУЮ, старую — нет; после delete — не находит.

## 9. Бэкенд

Санитизация MATCH: пользовательский ввод → разбиение по пробелам → каждый токен в `"…"` (phrase) → join пробелом (AND-семантика); символы `"` внутри токена удаляются. Запрос из спецсимволов (`"*`, `NEAR(`) → безопасно нейтрализован; пустой после санитизации → пустой результат ok.

## 10. Фронтенд

Строка поиска с debounce 300 мс; отображение сниппета? НЕТ в MVP — строка записи обычная (сниппет — будущая работа); очистка запроса ×-кнопкой; сочетание с фильтрами: поиск применяется к результату фильтров (клиентское сужение? НЕТ: серверный канал принимает query; фильтры периода применяются ПОСЛЕ в renderer поверх результата — решение: search возвращает по всей БД, фильтры-период/рука сужают на клиенте — при >500 результатах предупреждение «уточните запрос»; документируется).

## 11. API

`notes/search`: `{query: string ≤100, limit?: int ≤200}` → `{items: MeasurementDto[]}`; ошибки: только APP/INTERNAL (мусорный запрос — не ошибка, а пустой результат).

## 12. Управление состоянием

Ключ кэша `['measurements','search',query]`; debounce; отмена предыдущего запроса (AbortSignal-паттерн query — supported).

## 13. Бизнес-логика

Fallback LIKE: если MATCH-путь вернул 0 и запрос ≥2 символов → `LIKE '%q%'` по note (escape %/_); лимит результата 50 (UI предупреждает «показаны первые 50» при равенстве). Дедуп: MATCH+LIKE пути не смешиваются (или/или).

## 14. Безопасность

Санитизация MATCH (§9) — защита от FTS-синтаксис-инъекций; параметризованный LIKE с ESCAPE; лимиты длин — DoS-гигиена.

## 15. Производительность

MATCH по 50k записей — миллисекунды (индекс); LIKE-fallback ≤200 мс на 50k (приемлемо как fallback); debounce 300 мс.

## 16. Доступность

Поиск-инпут: label, `type="search"`, Esc очищает; результаты announcements: `aria-live="polite"` строка «Найдено N».

## 17. Интернационализация

Ключи: `search.placeholder`, `search.foundN` (ICU plural!), `search.truncated50`, `search.empty`.

## 18. Телеметрия

Лог debug: `notes/search durationMs hits=N queryLen=M` (без текста запроса — может содержать PHI-контекст).

## 19. Стратегия тестирования

Интеграционные (tmp-БД): миграция v2 создаёт FTS+триггеры; backfill индексирует существующие; CRUD-синхронизация (вставил→нашлось; обновил→новая версия найдена, старая нет; удалил→не найдено); санитизация: `test" OR` → безопасный результат; LIKE-fallback кейс; UI: debounce, очистка, foundN-plural.

## 20. Критерии приёмки

- [ ] Миграция v2: FTS-таблица+триггеры существуют; backfill находит старую заметку.
- [ ] CRUD-синхронизация (3 кейса §19) зелёная.
- [ ] «болит голова» находит заметку «болела голова»? — НЕТ (морфологии нет): находит только точный токен «голова» (тест фиксирует честное поведение + LIKE «болел» находит «болела»).
- [ ] Запрос `test" OR 1=1` → пустой/безопасный результат, без ошибки SQL.
- [ ] Empty-запрос → пустой результат ok; UI: Esc очищает, foundN с плюрализацией.
