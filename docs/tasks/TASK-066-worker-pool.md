## 2. Цель

Общий пул из 2 `worker_threads` с очередью задач (job API: тип, payload, прогресс, результат/ошибка), чтобы PDF-рендер, экспорт 50k CSV и тяжёлые series не блокировали main (NFR-4) и IPC оставался отзывчивым.

## 3. Бизнес-контекст

Генерация PDF — секунды CPU: если считать в main, окно «висит» и IPC-вызовы (ввод измерения!) стоят в очереди — недопустимо (арх. 03 §6). Пул общего назначения переиспользуют отчёты (067), экспорт (быстрый путь остаётся в main — маленькие), bench.

## 4. Технический контекст

- **Архитектура:** изоляция тяжёлых задач — `docs/architecture/03-modules.md` §6.
- **Модуль:** `main/shared/workerpool` (инфраструктура, не модуль фичи).
- **Обоснование:** worker_threads (не child_process): общий heap-канал structured clone дешевле, легче деплой; 2 воркера = параллельный PDF+экспорт без CPU-переподписки (ядра 2+ у целевого железа A — компромисс: N=2 фикс, не авто = предсказуемость). Альтернатива UtilityProcess (как LLM): для коротких CPU-задач тяжелее (процесс, не поток); LLM — отдельный UtilityProcess из-за нативного кода и RAM (арх. 07), здесь потоки достаточно.

## 5. Объём

- **Включено:** `WorkerPool`: инициализация 2 воркеров из entry `worker.ts` (ленивое создание при первой задаче); `run<TaskName>(name, payload, {onProgress?}): Promise<Result>` — реестр task-обработчиков в воркере (Map name→fn); очередь при занятости обоих (FIFO); таймаут опциональный (параметр, дефолт нет); отмена? Решение: кооперативная отмена — job получает abort-сигнал, обработчик может проверять (PDF-задача — не отменяется в MVP, документируется); ошибки воркера: uncaughtException в воркере → job падает, воркер перезапускается, очередь продолжает; тесты: параллельные задачи распределяются, ошибка не валит пул, порядок FIFO при 3 задачах/2 воркерах, прогресс-события.
- **Не включено:** перенос CSV-экспорта в пул (малые объёмы в main быстрее; 50k-экспорт может через тот же пул — точка расширения, комментарий), приоритеты задач.
- **Будущая работа:** динамический размер пула по os.cpus (решение против — предсказуемость; пересмотр при NFR-данных).

## 6. Файлы

- **Создать:** `main/shared/workerpool/{pool.ts,worker.ts,protocol.ts}` + тесты (в реальном worker_threads — интеграционные, плюс unit протокола).
- **Изменить:** `container.ts` (создание пула, graceful shutdown: terminate на will-quit после БД-закрытия).

## 7. Модель предметной области

Протокол (спецификация): `{jobId, name, payload} → {jobId, ok, value|error}` + `{jobId, progress: 0..1}`. Обработчики задач регистрируются map'ой — задачи определяются потребителями (067 добавит `pdf.render`).

## 13. Бизнес-логика

FIFO очередь при занятости; fail-fast ошибка задачи → отклонение конкретного promise; перезапуск воркера после краша (exit-событие) — с логом; повторное использование (warm) после первой задачи.

## 14. Безопасность

Payload — данные пользователя (записи для PDF) в памяти воркера — допустимо (тот же процесс-машина); воркеры БЕЗ доступа к ключу БД (правило §8) — атака-поверхность минимальна.

## 15. Производительность

Цель: IPC-ping латентность во время активного PDF <50 мс (тест: замер параллельно); накладные structured clone на 10 МБ payload ~десятки мс — приемлемо.
