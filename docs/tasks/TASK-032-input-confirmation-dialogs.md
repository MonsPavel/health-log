## 2. Цель

После сохранения с флагами из ответа add: модальный поток «Проверьте значения» — показать подсказку (опечатка/дубль) и выбор «Оставить» / «Удалить только что созданную запись»; при criticalValue — та же модальность показывает информационную панель срочности (полный текст FR-7.4 — TASK-041 расширит; здесь — каркас потока с кратким текстом).

## 3. Бизнес-контекст

Паттерн UC-01 A1/A2: сохранение уже произошло (атомарно и просто — TASK-029 §13), пользователь решает судьбу записи после факта: «Исправить» = удалить созданное + возврат к форме с сохранённым вводом. Никаких блокировок ввода (EC-03).

## 4. Технический контекст

- **Архитектура:** UC-01 альтернативы — SRS 06; удалить созданное = канал delete (готов — порт; хендлер delete появится в TASK-037 — НЕТ, нужен здесь!). УТОЧНЕНИЕ ОБЪЁМА: минимальный use case delete (без UI-расширений) входит в этот таск: канал `measurements/delete {id}` уже в contracts TASK-028; здесь реализуется его use case (repo.delete + события) — TASK-037 позже добавит full-edit к нему.
- **Обоснование:** второй вызов add не нужен (двухфазность отклонена — TASK-029 §13); delete-only-rollback прост и честен.

## 5. Объём

- **Включено:** use case `DeleteMeasurement` (repo.delete + события changed/versionBumped + NOT_FOUND-обработка) и его канал; компонент `ConfirmFlagsDialog`: сборка подсказок из флагов (typo → «Обычно около {median}…», duplicate → «Такая запись уже есть 2 минуты назад…»), кнопки: «Оставить» / «Удалить и исправить»; при criticalValue — блок срочности (сокращённый текст: «Давление ≥180/120 может быть опасным. При симптомах — немедленно обратитесь за помощью. Полная информация — на панели» — полный текст в TASK-041); интеграция в onSuccess формы TASK-031: флаги есть → открыть диалог; «Удалить и исправить» → delete + возврат значений в форму; тесты.
- **Не включено:** полный текст/номера экстренных служб панели (TASK-041), флаги-бейджи в истории (TASK-042).
- **Будущая работа:** «не показывать подсказки такого типа» настройка — post-MVP.

## 6. Файлы

## 7. Модель предметной области

DeleteResult = `{deleted: true}`; NOT_FOUND → err (запись уже удалена другим путём — UI показывает «уже удалена», не ошибка-краш).

## 8. База данных

Через порт.

## 9. Бэкенд

Delete: repo.delete → события → лог. Порядок с событиями: как в add.

## 10. Фронтенд

Модальность Radix Dialog: фокус-ловушка, Esc = «Оставить» (безопасное действие по умолчанию), aria-describedby для подсказок; кнопка опасного действия (удалить) НЕ в автофокусе; после «Удалить и исправить»: форма получает обратно введённые значения (из store черновика — он не очищался до подтверждения), фокус в sys.

## 11. API

## 12. Управление состоянием

После delete: invalidateQueries(['measurements']) + versionBumped-событие придёт из main.

## 13. Бизнес-логика

Комбинация флагов typo+duplicate — одна карточка с двумя строками (не два диалога подряд). criticalValue + typo → показываются обе секции: срочность первой. Пограничный: delete упал NOT_FOUND (запись уже удалена) → тост «Запись уже удалена», форма НЕ возвращает значения (нечему возвращаться — пользователь видит пустую форму).

## 19. Стратегия тестирования

Use case: delete ок (события), NOT_FOUND-ветка. Компонент: рендер подсказок из флагов-фикстур (typo-only, duplicate-only, оба, оба+critical); клик «Оставить» → onClose без delete; «Удалить и исправить» → invoke delete + onRollback(values); Esc → keep; фокус-ловушка (Tab зациклен).

## 20. Критерии приёмки

- [ ] Флаги typo → диалог с подстановками медианы/значения; «Оставить» — запись остаётся (list не изменился).
- [ ] «Удалить и исправить» → запись удалена (list-1), форма содержит прежние значения, фокус в sys.
- [ ] criticalValue='high' → секция срочности сверху (сокращённый текст; полный — TASK-041).
- [ ] Esc = «Оставить»; фокус зациклен в диалоге; возврат фокуса в форму.
- [ ] Delete NOT_FOUND → тост «уже удалена», без креша.
