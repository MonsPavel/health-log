## 2. Цель

Recovery-режим: при dbOk=false или MIGRATION_FAILED на старте — полноэкранный режим восстановления: объяснение → варианты «Восстановить из копии» (restore execute с recovery:true — сравнение с текущими данными пропускается) / «Начать заново» (удалить повреждённую БД — второе подтверждение) / «Показать технические детали» (раскрытие для диагпакета).

## 3. Бизнес-контекст

EC-14: повреждение — не приговор данных (есть копии — TASK-070/074); молчаливая «починка с потерями» запрещена. Пользователь проходит понятный путь без консоли (AC EC-14).

## 4. Технический контекст

- **Архитектура:** кризисные состояния — арх. 09 §10; restore execute — TASK-071 (точка расширения recovery:true).
- **Обоснование:** recovery-режим = приложение стартует БЕЗ рабочего контейнера (БД не открыта): флаг в контейнере `mode: 'recovery'` → UI рендерит только RecoveryScreen; все БД-каналы гвардятся (LOCKED-стиль) — надёжно и просто.

## 5. Объём

- **Включено:** контейнер: ветка dbOk=false или MIGRATION_FAILED → `mode: 'recovery'`, причина сохранена (corrupt|migration_failed, детали для раскрытия); все secure-каналы → `STORAGE/RECOVERY_MODE` (гвардия расширяется — инвентарь-тест); `RecoveryScreen`: текст объяснения (спокойный: «Не удалось открыть дневник. Данные скорее всего целы в резервной копии»), кнопки: «Восстановить из копии» (файл-пикер → пароль копии → execute recovery:true → перезапуск), «Начать с чистого дневника» (confirm ×2: «будут удалены повреждённые файлы и начата пустая база» → unlink db/wal/shm → relaunch), «Технические детали» (collapse: код, quick_check-вывод, версии — для diag); «Открыть папку с копиями» (reveal backups-каталога); e2e-тест повреждения (битый файл-фикстура подмена userData).
- **Не включено:** автоматическое лечение (reindex/repair-хаки — опасны, не делаем), восстановление без копии (чистый старт — осознанный выбор пользователя).
- **Будущая работа:** авто-поиск копий в userData/backups списком (пост-MVP удобство).

## 6. Файлы

- **Создать:** `src-renderer/app/recovery/RecoveryScreen.tsx` + тесты; гвардия-расширение; тесты контейнера-режима; e2e `recovery.spec.ts`.
- **Изменить:** `bootstrap/container` (режим), `TASK-071` restore — параметр recovery:true (пропуск compare-фазы, документы), регистрация каналов в recovery-режиме (только app/*, restore, wipe-подмножество).

## 7. Модель предметной области

`RecoveryContext {reason: 'corrupt'|'migration_failed', details: {quickCheck?, migrationVersion?}, appVersion}` — без PHI.

## 8. База данных

Повреждённый файл: НЕ удаляется автоматически при «Восстановить» — только при «Начать заново»; восстановление подменяет файл (execute 071 путь, текущая-страховка пропущена — нечего страховать).

## 9. Бэкенд

Каналы recovery-режима: app/meta, app/reveal, backup/restore(execute), data/wipe-execute-подмножество (чистый старт), diag — остальные LOCKED/RECOVERY_MODE.

## 10. Фронтенд

Режим-рендер: App проверяет контейнер-режим (через канал app/meta при старте — до роутера) → RecoveryScreen вместо Layout.

## 11. API

Расширения: ошибки secure-каналов в recovery → STORAGE/RECOVERY_MODE; restore recovery-параметр (071-расширение).

## 12. Управление состоянием

N/A.

## 13. Бизнес-логика

«Восстановить»: неверный пароль копии → инлайн (retry); копия новее-схемы → та же защита 071; успех → relaunch → обычный режим. «Начать заново»: два подтверждения (диалог + чекбокс-фраза) — необратимость повреждённых данных всё равно честная (они не читаются, но файлы удаляются).

## 14. Безопасность

Recovery-режим не расширяет поверхности: каналы сужены (инвентарь-тест списка разрешённых).

## 16. Доступность

## 17. Интернационализация

## 18. Телеметрия

Лог: recovery-mode enter, выбранное действие, исход.

## 19. Стратегия тестирования

Контейнер: corrupt-фикстура → mode recovery, secure-канал → RECOVERY_MODE, разрешённый → работает; restore recovery:true пропускает сравнение (тест 071-расширения). E2E: подменить userData-БД битой → старт → RecoveryScreen → восстановить из копии (созданной ранее в тесте) → данные копии; «начать заново» → онбординг.

## 20. Критерии приёмки

- [ ] Повреждённая БД → RecoveryScreen с причинами (e2e), secure-каналы закрыты (тест).
- [ ] «Восстановить из копии»: полный путь до данных копии (e2e).
- [ ] «Начать заново»: двойное подтверждение → онбординг (e2e).
- [ ] Техдетали раскрываются (quick_check-текст виден).
- [ ] MIGRATION_FAILED-ветка (фикстура-миграция с ошибкой) → тот же экран, причина migration_failed.
- [ ] Golden-тон: запрет паник-лексики (тест).
