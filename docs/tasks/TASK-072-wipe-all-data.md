## 2. Цель

`WipeAllData`: двухшаговое подтверждение → предложение экспорта → фактическое удаление всех данных пользователя (БД + wal/shm + ключ + логи + события + черновики localStorage) → приложение в состоянии «как после установки»; отказ на любом шаге ничего не удаляет.

## 3. Бизнес-контекст

Право на исчезновение (принцип 3, FR-6.5, UC-10): пользователь уходит/передаёт ПК — данные удаляются по-настоящему (NFR-1), а не «скрываются». Честность: предупреждение об ограничениях ФС (удалённый файл теоретически восстановим форензикой — документируем, шифрование делает это бессмысленным для содержимого).

## 4. Технический контекст

- **Архитектура:** FR-6.5, UC-10, NFR-1; Security wipe — арх. 08 §6 (строка «Остаточные данные»).
- **Обоснование:** удаление = закрытие БД + unlink файлов + relaunch (как restore-паттерн); шифрование делает «восстановленные» файлы мусором без ключа — ключ тоже удаляется → криптографически данные исчезают даже при файловой реставрации (сильная позиция, документируется).

## 5. Объём

- **Включено:** `WipeAllData`: фаза plan (не удаляет!): собирает список файлов к удалению (db, -wal, -shm, vault.key, logs/*, backups/ (копии — тоже данные пользователя! РЕШЕНИЕ: удаляются, с явным перечислением в подтверждении), localStorage-черновики — команда renderer'у), возвращает план; фаза execute (confirmed): закрыть БД (checkpoint+close) → unlink файлов по списку (по одному, лог каждого) → relaunch; после перезапуска: онбординг-состояние (новая БД+ключ создадутся автоматически — TASK-023/025 путь первого запуска); канал `data/wipe {phase: 'plan'|'execute'}`; коды `WIPE/FAILED` (частичный отказ — что осталось — в error.details); тесты.
- **Не включено:** удаление самого приложения/настроек ОС (вне компетенции — документация установщика, EC-26), гарантии ФС-форензики (документируем честно: криптографическая гарантия через удаление ключа).
- **Будущая работа:** подтверждение вводом фразы «УДАЛИТЬ» (если UX-ревизия потребует).

## 6. Файлы

- **Создать:** `main/modules/data-care/application/wipe-all.ts` + интеграционные тесты; contracts `data/wipe`.

## 7. Модель предметной области

`WipePlan {files: [{path: '<basename>', category: 'db'|'key'|'logs'|'backups'}], counts: {measurements}}` — пути от renderer не принимаются: план строит main из фактических каталогов (безопасность: renderer не командует файлами).

## 8. База данных

Закрытие: wal_checkpoint(TRUNCATE) → close → unlink трёх файлов. Новый старт: контейнер создаст новую БД+ключ (существующий путь первого запуска).

## 9. Бэкенд

Порядок execute: plan пересобран и сверён (файлы должны существовать из plan — расхождение → отказ, состояние изменилось) → диалог закрыт/БД закрыта → unlink → relaunch. Частичный unlink-сбой → собрать оставшиеся в ошибку (не молча), НЕ перезапускать (полуживое состояние хуже — пользователь видит ошибку, документация).

## 10. Фронтенд

N/A (073): рендерер дополнительно чистит localStorage-ключи (`hl.formDraft`, `hl.formPrefs`, `hl.theme` — всё) ПОСЛЕ подтверждённого execute и ПЕРЕД relaunch.

## 11. API

`data/wipe`: plan → `WipePlan`; execute → `{restarting: true}`; ошибки WIPE/FAILED {remaining: [...]}.

## 12. Управление состоянием

После relaunch — чистое приложение (query-кэш новый).

## 13. Бизнес-логика

Копии в userData/backups (в т.ч. pre-migration) — в плане (пользователь должен видеть: «будут удалены и резервные копии — экспортируйте нужные заранее»); предложение экспорта (кнопка «Сначала экспортировать» на UI 073 до запуска plan) — use case не блокирует. Двухшаговость: plan и execute — два явных вызова (не таймер) — защита от двойного клика.

## 14. Безопасность

Renderer не передаёт пути; unlink — только из фактического плана main; лог удалений — по basename (без значений). Ключ шифрования удалён = криптографическое стирание (§4).

## 19. Стратегия тестирования

Интеграционные (tmp-userData): plan после добавления данных → файлы перечислены (db+key+logs+backups-fixture); execute → файлы отсутствуют; relaunch-эмуляция → новая БД создаётся, count=0; частичный сбой (мок chmod-защита файла лога) → WIPE/FAILED с remaining, БД-файлы удалены? (порядок: БД последней — решение: порядок удаления: backups→logs→key→db — БД последней, чтобы сбой оставил читаемое состояние) — тест порядка; execute без plan → отказ.

## 20. Критерии приёмки

- [ ] Plan возвращает полный список категорий (fixture-файлы всех типов созданы заранее).
- [ ] Execute → все файлы удалены; эмуляция перезапуска → чистая БД, seed-профиль заново.
- [ ] Порядок удаления: db — последним (тест-мок сбоя на логах: БД цела).
- [ ] Execute без предварительного plan → отказ (требование двухшаговости).
- [ ] localStorage-ключи очищены (команда renderer — юнит хелпера).
