## 2. Цель

Vitest как единый тест-рантайм всех пакетов: `pnpm test` запускает всё; `pnpm test:coverage` собирает merged-отчёт; конфигурация готова принять юниты (node-окружение), интеграционные (node + tmp-файлы) и будущие тесты рендерера.

## 3. Бизнес-контекст

Стратегия тестирования (арх. 10 §1) смещена в чистые слои: домен и use cases тестируются без Electron миллисекундами. Это возможно только если тестовая инфраструктура существует до первого доменного кода (TASK-006), а не после. NFR-10 требует покрытия расчётов ≥90% — infrastructure coverage появляется здесь.

## 4. Технический контекст

- **Архитектура:** testing architecture — `docs/architecture/10-delivery.md` §1.
- **Пакеты:** все; размещение тестов — colocation `*.test.ts` рядом с кодом.
- **Обоснование:** Vitest вместо Jest — нативный ESM/TS без сборочных костылей, общий рантайм с Vite (TASK-007). Альтернатива Jest: зрелость, но ts-jest/esm-трение; компромисс принят в фикс. решениях.

## 5. Объём

- **Включено:** vitest как root-devDependency; `vitest.workspace.ts` с проектами (kernel, contracts, scales-data, desktop-main → include `apps/desktop/src/main/**/*.test.ts`, desktop-renderer → включается в TASK-013 с jsdom, пока закомментирован заготовкой); скрипты `test` (run-режим), `test:watch`, `test:coverage` (provider v8, reporter text+lcov, merged через `--coverage` на workspace); конфиг порогов **без гейта** (thresholds закомментированы с TODO-ссылкой на TASK-052: порог 90% включается, когда есть что мерить, — домен аналитики).
- **Не включено:** Playwright/e2e (TASK-035), тесты Electron main в живом процессе (позже, интеграционные — через контейнер TASK-027).
- **Будущая работа:** sharding в CI при >3 мин прогонов (порог — спринт 6).

## 6. Файлы

- **Создать:** `vitest.workspace.ts`, `packages/kernel/vitest.config.ts` (создаётся в TASK-006 по факту), базовый `vitest.shared.ts` (общие настройки: environment node, include-патерны).
- **Изменить:** корневой `package.json` (скрипты test/test:watch/test:coverage), devDependencies корня.

## 13. Бизнес-логика

Правила запуска: тесты не зависят от сети (запрещено глобальным setup-хуком: `globalThis.fetch` подменяется на throw-заглушку в тестовом окружении — гарантирует, что ни один тест не «позвонит домой», фронт FR-7.2); тесты изолированы от файловой системы пользователя (запрет на чтение реального userData — проверяется правилом: любые tmp-пути через `fs.mkdtemp(os.tmpdir())`).

## 14. Безопасность

Тестовая заглушка fetch (§13) — часть модели «приложение не ходит в сеть»: регресс-тест на появление сетевых вызовов в тестах = ранний детектор утечки сетевого кода в чистые слои.

## 15. Производительность

Прогон пустого набора ≤5 с; цель полного набора в течение P0–P2 ≤60 с (порог шардирования — спринт 6).

## 18. Телеметрия

## 19. Стратегия тестирования

Сама задача — инфраструктура стратегии; фиксирует конвенции: colocated tests, naming `*.test.ts`, интеграционные помечаются `*.int.test.ts` (отдельный include для выборочного запуска), fixture-каталоги `__fixtures__/` рядом.

## 20. Критерии приёмки

- [ ] `pnpm test` зелёный (0 тестов — не ошибка, отдельный проект без файлов пропускается).
- [ ] Демо-тест в kernel (временный, удаляется в TASK-006) проходит в <2 с.
- [ ] `pnpm test:coverage` создаёт merged `coverage/lcov.info`.
- [ ] Заглушка fetch: тест, вызывающий `fetch()`, падает с понятной ошибкой (проверяется временным тестом).
- [ ] `pnpm test` не обращается к сети (следствие заглушки) и к реальному userData (ревью конвенций).

## 24. Проверка

Автоматически: `pnpm test` exit 0; `pnpm test:coverage` создаёт артефакт; временный fetch-тест — падает с сообщением «network is disabled in tests», после проверки удаляется. Ручная: `pnpm test:watch` подхватывает новый `*.test.ts` без перезапуска. Откат: revert; TASK-006 (зависимый) просто не стартует до восстановления.
