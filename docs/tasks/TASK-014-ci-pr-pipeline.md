## 2. Цель

Workflow `pull_request`: lint → typecheck → depcruise → test (с coverage) → build renderer; кэширование; зелёный статус обязателен для merge. Время прогона на P0-объёме ≤5 минут.

## 3. Бизнес-контекст

«Зелёный main = всегда собираемый продукт» (арх. 10 §3) — дисциплина, которая для соло-разработчика заменяет команду ревьюеров: CI ловит то, что глаз пропустит. Все будущие гейты (E2E, крэш-тесты, red-set) наследуют этот каркас.

## 4. Технический контекст

- **Архитектура:** CI/CD — `docs/architecture/10-delivery.md` §3.
- **Инфраструктура:** GitHub Actions, runner ubuntu-latest (Electron-окна не нужны для шагов PR — юнит/интеграция headless; Windows-runner E2E — TASK-105, TD-6).
- **Обоснование:** один job с последовательными шагами вместо матрицы job'ов — экономия startup-времени и прозрачный лог; разбиение на job'ы — при >8 мин.

## 5. Объём

- **Включено:** `.github/workflows/pr.yml`: триггеры pull_request + workflow_dispatch; concurrency-group по ветке (cancel-in-progress); шаги: checkout → setup Node 20 (corepack enable → pnpm 9) → `pnpm fetch` (кэш store через actions/cache ключом `pnpm-lock.yaml`) → install `--frozen-lockfile` → `pnpm lint` → `pnpm typecheck` → `pnpm depcruise` → `pnpm test` (vitest run, coverage включён) → `pnpm build:renderer`; upload артефактов coverage (lcov) и отчётов vitest; `--no-sandbox`-флаги Electron-тестам не нужны (их нет в PR-наборе). Настройка ветки main: required checks (перезечислить имена шагов-джобов), merge только зелёный.
- **Не включено:** Windows-runner и Playwright e2e (TASK-105, TD-6), ночная eval (TASK-092), релизный workflow (TASK-105), кэш Electron-бинарников (не нужен — Electron не скачивается на PR-шагах).
- **Будущая работа:** breaking-change-гейт (размер бандла — TASK-036 интегрируется сюда после P1).

## 6. Файлы

- **Создать:** `.github/workflows/pr.yml`.
- **Изменить:** корневой `package.json` (недостающие скрипты, если TASK-003/004/005 ввели иные имена), настройки репозитория GitHub (required checks — ручной шаг, зафиксировать в CONTRIBUTING TASK-015).

## 7–12. Домен / БД / Бэкенд / Фронтенд / API / Состояние

N/A — инфраструктурная задача; проверяемые команды уже существуют из TASK-003/004/005 и TASK-007 (build:renderer).

## 13. Бизнес-логика

Правила пайплайна: (1) frozen-lockfile — сборка воспроизводима; (2) отказ любого шага = отказ PR; (3) re-run только полный (без skip-cache между ретраями — иначе «зелёный по кэшу»); (4) секреты не используются (нечему утекать на PR-этапе).

## 14. Безопасность

`permissions: contents: read` в workflow (минимальные права); действия пинованы по мажорной версии; никаких pull_request_target (не выполнять код PR в привилегированном контексте — OWASP CI/CD).

## 15. Производительность

Бюджет ≤5 мин (AC): достигается кэшем pnpm-store и последовательным одиночным job'ом; при превышении — сначала кэш сборки tsc (`.tsbuildinfo`), затем шардирование.

## 18. Телеметрия

Статусы проверок GitHub — единственная «метрика» процесса; coverage-артефакты ручного просмотра.

## 19. Стратегия тестирования

Тест пайплайна = сам пайплайн на реальных PR; проверка красного срабатывания — контрольный PR с искусственным нарушением (§20). Регрессия: главный branch-прогон после merge (тот же workflow на push в main).

## 20. Критерии приёмки

- [ ] Контрольный PR: `pnpm lint`-нарушение (фикстура из TASK-003) → статус красный с шагом lint.
- [ ] Контрольный PR: падающий тест → красный шаг test.
- [ ] Чистый PR: все шаги зелёные, время ≤5 мин, кэш store попадает (второй прогон — install <30 с).
- [ ] coverage/lcov.info доступен как артефакт прогона.
- [ ] Required checks настроены для main (скриншот/список в CONTRIBUTING).

## 22. Риски

## 23. Будущие соображения

Матрица ОС — не до P7 (E2E на Windows — TASK-105); кэш tsc incremental; отчёты покрытия в PR-комментарии (опционально, не MVP).

## 24. Проверка

Автоматически: три контрольных PR (чистый + 2 нарушения) — ожидаемые статусы. Ручная: лог прогона читается сверху вниз без скачков (шаги именованы). Откат: disable workflow — разработка продолжается локально (CI не блокирует аварийные фиксации: admin-merge возможен).
