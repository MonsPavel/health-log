# Локальная LLM: dev-документация (llm-worker, TASK-077)

Движок воркера `llm-worker` — node-llama-cpp (prebuilt llama.cpp) поверх
MessagePort-протокола TASK-076. Код: `apps/desktop/src/main/llm-worker/{main,engine,llama-engine}.ts`.

## Проверено на этой машине (§22 риск ABI)

- Prebuilt-бинд `llama-addon.node` (node-llama-cpp 3.22.1, win-x64, CPU)
  загружается и в node 24 (`getLlama({build:'never'})` → `buildType: prebuilt`),
  и в рантайме **Electron 44.4.5** (пробный скрипт `pnpm exec electron` с
  `getLlama` в main-процессе; см. коммиты TASK-077): пересборка не требуется.
- Нюанс: `getLlama` в **главном** процессе Electron нельзя вызывать до
  `app ready` (его тест бинда спавнит utilityProcess). В нашей архитектуре это
  неактуально: `getLlama` зовётся внутри процесса llm-worker (UtilityProcess),
  где тест бинда падает обратно на `node:child_process` (ограниченный
  `electron`-модуль), а вызов и так происходит по запросу `load`, не на старте.

## Где взять GGUF (ручная загрузка разработчиком)

Модель **не в репо и не в CI** (решение §5 TASK-077): разработчик скачивает GGUF
вручную на dev-машину и передаёт путь через env.

- Источник: HuggingFace-репозитории с GGUF (например, `Qwen/Qwen3-*-GGUF`,
  квантования `bartowski/*-GGUF`). Целевой класс — инструктивные 3–4B Q4
  (~2–3 ГБ на диске, референс SRS 05 NFR-5); dev-фикстура для быстрых прогонов —
  1B Q4 (~700 МБ).
- Положить куда угодно на диске (вне репозитория). Путь — только локальный:
  воркер не имеет сети (§14), sha256-проверка внешних GGUF появится с реестром
  моделей в TASK-080 — до неё dev-модель ставится руками и ей доверяют.
- Требование формата: GGUF с корректным magic-заголовком (`GGUF`, первые 4
  байта) — движок валидирует заголовок до передачи нативу (§13: битый файл →
  ошибка `AI/MODEL_INVALID`, воркер не крашится).

## Как включить

### `[model]`-тесты (vitest, ручной запуск)

```bash
# Git Bash / cmd: путь к GGUF через env; без него тесты движка пропускаются
HL_TEST_MODEL=D:/models/model-q4.gguf pnpm exec vitest run llama-engine
```

Покрывается: load → generate → стрим → done(stop); замер первого токена/ток/с
(строка `[model] замер: {...}` в консоли); cancel < 1 с; idle-unload по env.

### Переменные окружения

| Переменная | Значение | Назначение |
|---|---|---|
| `HL_TEST_MODEL` | путь к GGUF | включает `[model]`-тесты (в CI не задана — пропущены) |
| `HL_LLM_IDLE_UNLOAD_MS` | целые мс > 0 | сокращённое окно авто-выгрузки по простою для ручной проверки (дефолт 300 000 = 5 мин, §5) |

### Логи воркера

pino-корень в UtilityProcess не инициализирован: движок пишет JSON-строки в
stdout воркера (наследуется stdout'ом main при `pnpm dev`). Операционные
события (spawn/exit/статусы) логирует main-клиент в категорию `ai` как обычно.
Пример строки генерации: `{"level":"info","category":"ai","message":"llm engine: генерация завершена","requestId":"…","tokens":N,"tps":…,"firstTokenMs":…}` —
текст промпта/ответа в лог не попадает (§14/§18).

## Конфиг инференса (дефолты, §4/§7 TASK-077)

## Ручная приёмка (§20 TASK-077)

1. `[model]`-прогон: стрим виден в логе воркера (`token`-сообщения протокола).
2. Cancel останавливает генерацию < 1 с (тест `[model]` печатает факт).
3. Idle-unload: `HL_LLM_IDLE_UNLOAD_MS=1500` + `[model]`-тест idle — после окна
   модель выгружена, следующая генерация отвечает `AI/NO_MODEL` до нового load.
4. RAM после unload возвращается (Диспетчер задач: память процесса llm-worker
   падает после `unload`/idle-unload — проверка руками).
5. Битый GGUF (первые байты ≠ `GGUF`) → ошибка `AI/MODEL_INVALID`, воркер жив
   (автотест `engine.test.ts`, CI).
