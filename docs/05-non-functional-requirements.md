# 05. Нефункциональные требования

**Статус:** черновик v0.1 · 2026-09-24 · ветка `docs/planning`

## Референсное железо

Целевые метрики производительности определены относительно двух конфигураций:

- **Железо A** (минимум для приложения без ИИ): 2-ядерный CPU, 4 ГБ RAM, SSD, Windows 10 x64.
- **Железо B** (референс для ИИ): 4-ядерный CPU уровня 2019+ (например, Core i5-9400 / Ryzen 5 3600), 16 ГБ RAM, SSD, без дискретной GPU.

Модель по умолчанию для целевых метрик ИИ: инструктивная LLM порядка 3–4 млрд параметров в 4-битном квантовании (~2–3 ГБ на диске). *Почему:* единственный класс моделей, который сегодня даёт связный русский текст на CPU без GPU в разумное время; меньшие модели «левают», большие не тянутся на целевом железе.

---

## NFR-1. Приватность по умолчанию

- Вся обработка данных — на устройстве. Никакой телеметрии (FR-7.2). Сеть — только из белого списка FR-7.3, по явному действию.
- Удаление пользователем = фактическое удаление данных.
- **Проверяемость:** релизная сборка проходит сетевой аудит: наблюдаемый трафик совпадает с журналом FR-7.1 и белым списком.

## NFR-2. Безопасность хранения

- Данные в покое зашифрованы; шифрование включено по умолчанию, без действий пользователя.
- Резервные копии (FR-6.4) зашифрованы тем же механизмом.
- Опциональный пароль на запуск (FR-7.5) при включении усиливает защиту ключа; пользователь предупреждается: **забытый пароль = невосстановимые данные**.
- Установщики подписаны; обновления проверяют подпись перед применением (NFR-11).
- *Почему:* медицинские данные — специальная категория; шифрование «включено по умолчанию» защищает пользователя, который никогда не зайдёт в настройки.

## NFR-3. Надёжность данных

- Внезапное отключение питания/крах процесса не приводит к потере ранее сохранённых измерений и повреждению хранилища.
- Черновик незаполненного ввода восстанавливается после краха.
- При обнаружении повреждения хранилища: явное сообщение, предложение восстановиться из копии, никаких тихих «починили с потерями».
- *Проверка:* тесты отключения питания в момент записи; целевой результат — ноль потерянных сохранённых записей.

## NFR-4. Производительность интерфейса

| Операция | Цель | Железо |
|---|---|---|
| Холодный старт приложения (без ИИ) | ≤3 с | A |
| Отклик UI на действия ввода | <100 мс | A |
| Построение графика, 1000 точек | <1 с | A |
| Генерация PDF-отчёта | <30 с | A |
| Экспорт 50 000 записей в CSV | <60 с | A |

*Почему:* «отклик <100 мс» — граница ощущения мгновенности; ввод — самое частое действие, его торможение убивает привычку.

## NFR-5. Производительность и ресурсы ИИ

- Первые токены ответа: ≤10 с; полный ответ на типовой вопрос: ≤60 с (Железо B, модель по умолчанию).
- RAM под инференс: ≤4 ГБ; после генерации память освобождается.
- UI остаётся отзывчивым во время генерации; после закрытия приложения фоновые вычисления отсутствуют.
- Установочный размер без модели: ≤200 МБ.
- На Железе A (без ИИ-возможностей) приложение функционально полностью, кроме генераций; пользователь получает честное сообщение о недостаточности железа, а не бесконечное «ожидание».
- *Почему:* разрыв между «демо на топе» и «работой у Елены на ноутбуке 2018 года» — главный производственный риск R-3; честные ожидания лучше тихих тормозов.

## NFR-6. Доступность и удобство

- Цели нажатия ≥44×44 CSS-пикселей; контраст WCAG 2.1 AA; полная управляемость с клавиатуры; скринридер (NVDA) — S.
- Ввод измерения ≤15 с (сквозная цель, проверяется на П1).
- Язык интерфейса — простой; каждый термин при первом появлении поясняется («СДА — «верхнее» давление»).
- *Почему:* доступность здесь — не комплаенс, а профиль ядра аудитории (П1, П3).

## NFR-7. Портируемость

- **Обязательно:** Windows 10/11 x64, включая масштабирование экрана 125–200% (ноутбуки с HiDPI — норма для П1/П2).
- **Желательно:** macOS 14+ (Apple Silicon), Linux (актуальные LTS Ubuntu/Fedora).
- **C:** portable-версия без установки.
- *Почему:* аудитория дневника давления на десктопе в РФ — Windows доминирует; кроссплатформенность желательна, но не должна тормозить MVP (OQ-1).

## NFR-8. Локализация

- Вся видимая текстура выносима из логики; добавление языка не требует изменений кода фич.
- Русский — полное качество в MVP; английский — пост-MVP.
- *Почему:* i18n «потом» — классическая дорогая перестройка; требование фиксирует только отделимость текста, не рамки архитектуры.

## NFR-9. Масштаб данных

- 50 000 записей (≈10+ лет по 4–8 измерений в день с заметками): старт, история, фильтры, графики — в целях NFR-4 без деградации.
- *Почему:* целевой сценарий «дневник на годы»; деградация на третьем году — потеря доверия без возможности объяснить.

## NFR-10. Сопровождаемость и корректность вычислений

- Модуль расчётов (статистика, классификация) — детерминированный, покрыт модульными тестами (цель ≥90% по строкам), включая тесты на медицинских реперных примерах.
- Версии справочных шкал и ИИ-модели фиксируются в каждой сборке и видны пользователю в разделе «О приложении».
- *Почему:* ошибка в среднем за период — не «баг в UI», а подрыв клинического доверия; реперные примеры защищают от тихих регрессий.

## NFR-11. Обновления

- Проверка обновлений — по явному согласию (по умолчанию выключена или с явным запросом при первом запуске), с показом «когда/что проверяли» (журнал FR-7.1).
- Применение обновления — с подтверждением пользователя; проверка подписи обязательна.
- *Почему:* даже «невинная» проверка обновлений — сетевой след (IP-адрес); пользователь, поверивший в локальность, не должен обнаруживать неожиданные соединения.

## NFR-12. Диагностика и ошибки

- Сообщения об ошибках — человеческие, с следующим шагом; стек-трейсы пользователю не показываются.
- Локальные журналы не содержат значений измерений и текста заметок.
- Экспорт диагностического пакета для баг-репорта — по явному действию (C).
- *Почему:* журнал без PHI можно безопасно прикладывать к issue; иначе поддержка вынудит пользователей публиковать их давление в интернете.
